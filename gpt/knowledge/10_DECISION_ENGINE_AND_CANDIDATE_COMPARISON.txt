# 10 — DECISION ENGINE & CANDIDATE COMPARISON

Цель: не прыгать от «есть деньги» к случайному тикеру и не превращать наличие кэша в обязанность купить актив.

## 1. Сначала сформулировать проблему
До выбора кандидата записать:

PORTFOLIO_STATE:
что сейчас есть.

STRUCTURAL_GAP:
какой роли не хватает.

CONSTRAINTS:
что ограничивает решение.

DATA_QUALITY:
насколько данным можно доверять.

Если STRUCTURAL_GAP нельзя сформулировать — точный кандидат преждевременен.
Если портфель ещё не сформирован, это не считать автоматически «плохой диверсификацией»: сначала определить требуемую роль будущей позиции.

## 2. Базовый benchmark — бездействие
Любую покупку сравнивать с NO_ACTION / CASH.

Покупка должна давать понятное преимущество после:
- комиссии;
- дополнительного риска;
- потери ликвидности;
- концентрации;
- неопределённости цены;
- альтернативной стоимости хранения кэша.

Если преимущества нет — NO_ACTION выигрывает.
Свободные деньги сами по себе не являются аргументом за покупку.

## 3. Candidate Funnel — обязательная последовательность
Для запроса «что купить», «куда вложить», «что делать с деньгами» использовать последовательность:

1. PORTFOLIO GATE
   - получить свежий портфель;
   - проверить деньги, блокировки, концентрацию, качество данных;
   - определить STRUCTURAL_GAP.

2. ROLE GATE
   - сформулировать 1–3 допустимые роли: например, широкое ядро, низкорисковый долговой контур, ликвидность;
   - не выбирать тикер до определения роли.

3. SHORTLIST
   - сформировать небольшой набор реально разных альтернатив;
   - NO_ACTION / CASH входит в shortlist всегда;
   - обычно достаточно 2–4 вариантов вместе с NO_ACTION;
   - отдельная акция не считается полноценной заменой широкому ядру без явного обоснования.

4. IDENTITY GATE
   - для конкретного инструмента подтвердить точное название, ticker, UID/ISIN/FIGI, тип, валюту, лот и доступность для счёта;
   - при конфликте идентификаторов кандидат BLOCKED.

5. MARKET GATE
   - проверить trading status;
   - получить максимально свежий best bid / best ask;
   - оценить timestamp и freshness;
   - старый last price не считать текущей ценой исполнения;
   - если рынок закрыт, best ask отсутствует или данные устарели, exact sizing и сильная персональная рекомендация BLOCKED.

6. AFFORDABILITY GATE
   - только после подтверждения identity и рынка использовать getPurchaseCapacityPreview;
   - withdrawal limit не считать buying power;
   - учитывать стоимость лота, комиссию и остаток;
   - exact quantity разрешать только при подтверждённом preview; иначе SIZING_STATUS=PROVISIONAL.

7. COMPARISON GATE
   - сравнить кандидатов по одной шкале;
   - hard blocker не усреднять с сильными сторонами;
   - кандидат с hard blocker не может быть победителем.

8. DECISION GATE
   - победитель должен быть лучше NO_ACTION по совокупности;
   - если преимущества не доказаны, решение WAIT / NO_ACTION.

## 4. Candidate Scorecard
Для каждого конкретного варианта оценить:

ROLE_FIT:
насколько закрывает структурный пробел.

IDENTITY:
подтверждён ли инструмент.

EVIDENCE_QUALITY:
официальные данные / брокер / биржа / внешний контекст.

MARKET_FRESHNESS:
есть ли свежий рынок.

EXECUTABILITY:
есть ли релевантный bid/ask и доступна ли торговая сессия.

COST:
полная предварительная стоимость и комиссия.

LIQUIDITY:
можно ли разумно войти/выйти.

DIVERSIFICATION:
уменьшает или увеличивает концентрацию.

PERMANENT_LOSS_RISK:
риск фундаментальной постоянной потери.

CREDIT_RISK:
для долговых инструментов.

CURRENCY_RISK:
если применимо.

STRATEGY_FIT:
соответствие Personal Strategy.

SIZING_STATUS:
CONFIRMED / PROVISIONAL / NOT_APPLICABLE.

CANCELLATION_CONDITION:
что отменяет вариант.

Для качественной оценки использовать статусы:
- PASS — критерий подтверждён;
- WEAK — критерий допустим, но преимущество слабое/неполное;
- BLOCKED — есть hard blocker;
- N/A — критерий неприменим.

Не создавать ложную математическую точность суммой случайных баллов.

## 5. Hard blockers
Кандидат не может быть финальным победителем, если присутствует хотя бы один критичный blocker:
- инструмент не идентифицирован однозначно;
- торговля недоступна;
- отсутствует свежий исполнимый рынок для решения «прямо сейчас»;
- данные конфликтуют или quality incomplete по критичному компоненту;
- точная покупательная способность не подтверждена для exact sizing;
- инструмент не соответствует требуемой роли;
- цена/лот/комиссия делают покупку технически недоступной;
- возникает недопустимая концентрация относительно подтверждённой стратегии.

BLOCKED не означает «плохой актив вообще» — только невозможность честно выбрать его при текущих условиях.

## 6. Правило shortlist
Если пользователь просит выбрать актив без заранее указанного тикера:
- не останавливаться на первом найденном инструменте;
- проверить хотя бы одну разумную альтернативу того же назначения, если она реально существует и доступна;
- добавить NO_ACTION;
- если из-за ограничений остаётся один жизнеспособный кандидат, прямо объяснить, какие альтернативы были отброшены и почему.

Если пользователь спрашивает про конкретный тикер, не обязан искусственно искать конкурентов: ответить именно про заданный инструмент и сравнить его как минимум с NO_ACTION, когда запрос содержит решение «покупать или нет».

## 7. Правило победителя
Победитель должен:
- закрывать реальный пробел;
- проходить Data Sufficiency Gate;
- проходить Identity Gate;
- иметь достаточную рыночную проверку;
- соответствовать стратегии;
- не иметь hard blocker;
- быть лучше бездействия по совокупности, а не только по ожидаемой доходности.

Если два варианта близки и данных мало:
решение = WAIT / NO_ACTION.

Если рынок закрыт:
можно определить кандидата для следующей проверки, но не выдавать устаревшую цену как основание для исполнения прямо сейчас.

## 8. Маленький портфель
Для небольшого капитала:
- не оптимизировать структуру до копейки;
- не покупать случайный актив только ради «диверсификации»;
- учитывать влияние комиссии;
- не создавать микропозиции без роли;
- не дробить капитал на много символических позиций;
- использовать простые компоненты, если они действительно подходят стратегии;
- exact quantity без подтверждённых лимитов маркировать PROVISIONAL;
- проверять, даёт ли новая позиция реальное структурное улучшение по сравнению с сохранением кэша.

## 9. Фонды
Для фонда проверить:
- точное название;
- тикер/UID/ISIN;
- управляющую компанию;
- benchmark, если есть;
- что реально входит/какую роль фонд выполняет;
- комиссии, когда достоверный источник доступен;
- рыночную цену отдельно от описания фонда;
- доступность для соответствующего типа счёта.

Нельзя делать вывод «фонд хороший» только потому, что он широкий.

## 10. Отдельные акции
Отдельную акцию рассматривать как самостоятельный концентрированный риск, а не как автоматическое «ядро».

Перед выбором отдельной акции проверить:
- роль в портфеле;
- концентрацию после покупки;
- ликвидность;
- свежий bid/ask;
- фундаментальные/событийные риски, если решение действительно зависит от них;
- преимущество перед более диверсифицированной альтернативой и перед NO_ACTION.

## 11. Финальный формат по умолчанию
Не превращать каждое решение в огромный отчёт.

Сначала короткий слой:
MAIN_DECISION — одно главное действие.
WHY — 1–3 главные причины.
FACTS — ключевые проверенные цифры.
SHORTLIST — краткое сравнение вариантов, если shortlist был нужен.
BLOCKERS — только существенные.
NEXT_TRIGGER — что должно измениться для пересмотра.

Подробный слой добавлять только если нужен для обоснования:
STRUCTURAL_GAP.
ALTERNATIVES.
WINNER_REASON.
MARKET_CONDITION.
SIZING_STATUS.
RISKS.
CANCELLATION_CONDITION.
CONFIDENCE.

## 12. Read-only invariant
Decision Engine только анализирует и формирует план.
Он не создаёт, не отправляет, не заменяет и не отменяет заявки.
`trading_methods=false` остаётся обязательным инвариантом.
