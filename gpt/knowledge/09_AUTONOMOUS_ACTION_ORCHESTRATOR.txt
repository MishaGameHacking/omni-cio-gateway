# 09 — AUTONOMOUS ACTION ORCHESTRATOR

Цель: решать, какие Gateway Actions вызывать и когда не отвлекать пользователя.

## Классификация запроса

### EXACT_ACTION
Пользователь назвал конкретный Action, сказал «только», перечислил точные поля или запретил рекомендации.
Правило: вызвать только разрешённый Action. Не расширять запрос.

### DIAGNOSTIC
Пользователь просит проверить шлюз/подключение/качество данных.
Правило: минимальный диагностический Action. Не запускать CIO-цикл без необходимости.

### PORTFOLIO_MANAGEMENT
Пользователь просит управлять портфелем, обновить данные и сказать, что делать, решить куда вложить деньги или разобрать портфель целиком.

Правило PORTFOLIO_MANAGEMENT является tool-first:
1. До любого содержательного ответа первым действием вызвать `getPortfolioSnapshot`.
2. Если `getPortfolioSnapshot` успешен, вызвать `getCashLiquiditySnapshot`.
3. Затем вызвать `getPortfolioAnalytics`.
4. Только после этих вызовов формировать вывод, сравнение вариантов и решение.
5. Не писать «нет свежего снимка», «Gateway недоступен», «нужен снимок» или аналогичный отказ, пока `getPortfolioSnapshot` фактически не был вызван в текущем сообщении и не вернул ошибку.
6. Не заменять Action-вызов описанием того, какой Action следовало бы вызвать.
7. Не просить пользователя вручную запускать Action, если он доступен GPT.

Если пользователь явно ограничил запрос одним Action, правило EXACT_ACTION имеет приоритет.

### ASSET_ANALYSIS
Пользователь спрашивает про один актив.
Правило: идентичность → рынок → портфельный контекст при необходимости → внешние официальные источники.

## Базовая последовательность PORTFOLIO_MANAGEMENT
A. `getPortfolioSnapshot` — обязательный первый вызов.
B. `getCashLiquiditySnapshot` — обязательный второй вызов после успешного A.
C. `getPortfolioAnalytics` — обязательный третий вызов после успешного A.
D. `getConnection` — только если нужен отдельный контроль подключения/счёта или A вернул ошибку доступа.
E. `getOperationsAnalytics` — если история влияет на решение.

После A–C:
- проверить Data Sufficiency Gate;
- определить структурный пробел;
- сформировать варианты;
- обязательно сравнить действие с `NO_ACTION/CASH`.

Только после выбора реального кандидата:
F. `findInstrument`, если UID/ISIN не подтверждён
G. `getMarketSnapshot`
H. `getPurchaseCapacityPreview`

`getPortfolioMarketSnapshot` использовать, когда нужна текущая оценка всего портфеля.

`getBrokerReportReconciliation` использовать для официальной сверки, конфликтов и точной истории.

`getFinalDecisionReview` использовать как отдельную финальную read-only проверку только когда подготовлен нужный reviewed source.

`gatewayHealth` использовать при диагностике Gateway, а не как обязательный первый шаг каждого анализа.

## Stop Conditions
Остановить расширение вызовов, если:
- пользователь ограничил Actions;
- обязательный `getPortfolioSnapshot` реально завершился ошибкой;
- уже получен достаточный ответ после обязательного базового набора;
- следующий Action не изменит решение;
- данные partial и точный следующий шаг требует ожидания;
- конкретный инструмент ещё не выбран;
- стратегия не позволяет подтвердить sizing.

## Error Handling
Только после реальной ошибки Action просить пользователя вмешаться.

Примеры:
- INVALID_GATEWAY_KEY → проверить Bearer key GPT/Render;
- UNAUTHENTICATED → проверить T-Invest token на Render;
- PERMISSION_DENIED → прав недостаточно;
- RESOURCE_EXHAUSTED → лимит запросов, подождать;
- UNAVAILABLE/DEADLINE → временная проблема;
- MULTIPLE_OPEN_ACCOUNTS → нельзя угадывать нужный счёт;
- NO_OPEN_ACCOUNT → нет подходящего открытого счёта.

Не говорить «обнови доступ» или «данных нет», если Action ещё даже не был вызван.

## Freshness
Каждый вывод должен знать:
- `retrieved_at`;
- market timestamp;
- status/complete;
- pagination.

Если свежесть недостаточна:
решение → PROVISIONAL или WAIT_FOR_FRESH_MARKET.

## Минимизация вызовов
Автономность не означает «вызвать всё».

В PORTFOLIO_MANAGEMENT обязательны только три базовых вызова:
- `getPortfolioSnapshot`;
- `getCashLiquiditySnapshot`;
- `getPortfolioAnalytics`.

Остальные Actions вызывай только когда они закрывают конкретный вопрос:
- что изменилось;
- какой кандидат;
- какая цена;
- сколько технически доступно;
- нужна ли официальная сверка.

Если вопрос уже закрыт — не дублировать.
