## Целевая архитектура

### На Android-устройстве

- read-only T-Invest token;
- реальные счета, позиции, деньги, операции и выплаты;
- цели/резерв;
- локальная история и portfolio calculations;
- сценарные расчёты;
- локальные уведомления.

Базовый local-first режим не требует аккаунта OMNICIO, email или пароля.

Sensitive local data шифруются; T-Invest token защищается Android Keystore и не передаётся Timeweb в базовом режиме.

### На Timeweb

- разрешённые общие источники;
- отчётность/корпоративные события;
- общий instrument/issuer intelligence;
- Timeweb AI Gateway;
- API версий общих фактов;
- минимальные entitlement/push данные только для явно включённых функций.

Один публичный документ анализируется один раз и используется всеми устройствами.
GPT не получает broker token, баланс или полный портфель пользователя.

## Интерфейс

Три вкладки:

- **Обзор** — капитал, доступные деньги, актуальность и одно существенное состояние;
- **Портфель** — весь локальный портфель без тарифного лимита числа позиций;
- **Помощник** — автоматическая лента важных событий и объяснений без пользовательского chat input.

Дополнительные настройки:

- T-Invest connection;
- privacy/local data;
- цели/резерв;
- уведомления;
- подписка;
- версия/источники.

Дизайн должен быть компактным и привычным для инвестиционного приложения, но не копировать товарные знаки, графику или защищённые элементы Т-Банка.

## Analytics-first и регулируемый gate

Базовый production развивает самостоятельную аналитику:

- фактический локальный портфель;
- концентрации;
- выплаты;
- общие факты/отчётность;
- существенное ухудшение эмитентов;
- stress/scenario calculators;
- сравнение вариантов, выбранных самим пользователем.

Автоматически выбранные системой персональные BUY/SELL/HOLD, конкретные количества и замены не выдаются обычным production Android build при закрытом regulated gate.
Полный optimizer можно разрабатывать и тестировать на synthetic/research data, не делая эту функцию доступной реальным пользователям.
Мобильное выполнение алгоритма само по себе не считается доказательством освобождения от требований к ИИР.

## Privacy-first

Цель — не «обойти 152-ФЗ», а минимизировать серверные данные.

В local-first режиме:

1. T-Invest data идут прямо с официального API на устройство;
2. персональный портфель остаётся в локальной зашифрованной БД;
3. Android запрашивает у Timeweb только общий intelligence по instrument/issuer IDs;
4. персональная математика выполняется локально.

Если отдельная функция всё же передаёт на сервер push token, entitlement/payment id, support data или иные относимые к пользователю сведения, соответствующие требования к ПДн применяются к фактической обработке. Нативное приложение не объявляется автоматическим освобождением от 152-ФЗ.

## T-Invest

Используется только read-only credential.
Trading/transfer authority не требуется.

Пользовательский T-Invest API используется для его собственного портфеля на устройстве.
Timeweb не ретранслирует пользовательский T-Invest API как общий рынок.
Общая аналитика использует отдельные источники с подтверждёнными правами.

## Фоновая работа

Timeweb круглосуточно обрабатывает общий рынок и существенные события.
Android выполняет персональную синхронизацию через WorkManager/open/sync opportunities.
Точное выполнение periodic work по минутам не обещается Android.

Optional fast alerts могут использовать RuStore Push.
Push payload не должен содержать баланс, позиции или broker token.

## Как создаётся Android-приложение

Android source code разрабатывается в этом репозитории на Kotlin + Jetpack Compose.

Проверяемый цикл:

`feature branch → PR → Android CI → debug APK artifact → установка на физический телефон → feedback → новый commit`.

Для обычной проверки OWNER не обязан собирать проект вручную: CI должен создавать устанавливаемый debug APK для exact commit SHA.

Android Studio рекомендуется на ноутбуке OWNER для Compose Preview, Emulator, USB-debugging, Logcat и финальной работы с release/upload signing material. Visual Studio не является канонической IDE Android-проекта.

Для RuStore готовится подписанный AAB и при необходимости APK. Debug build никогда не публикуется как production release.

T-Invest token и private signing key не передаются в чат/PR и не коммитятся.

Проверка конфигурации не доказывает доставку в реальные ящики: перед публикацией требуется проверить отправителя, доставку и сообщения об ошибках без раскрытия секретов.

Общие параметры интерфейса находятся в `web/config.js`, переводы RU/EN — в `web/i18n.js`, маршруты и примитивы — в `web/workspace.js`, сетевые и пользовательские сценарии — в `web/app.js`. Цвета и токены оформления централизованы в `web/tokens.css`. `web_assets.py` формирует согласованную версию всех статических файлов; обновление PWA не должно подменять сохранённые данные аккаунта.

### Миграции и выпуск

Принятые SQL-миграции 0001–0028 остаются неизменными. `0029_email_auth.sql` добавляет почтовые идентичности, проверочные задания и постоянные ограничения частоты; `0030_portfolio_read_only.sql` допускает неизвестную текущую стоимость и денежные показатели. Прежние пользовательские записи не мигрируют по одному совпадению адреса.

Runtime и deployer проверяют общий контракт `schema.py`, включая таблицы, необходимые поля и принудительную изоляцию финансовых данных. В текущем Timeweb bootstrap миграции и приложение используют одного владельца таблиц `omnicio_app`; FORCE RLS сохраняется. Серверные auth-таблицы предназначены для доверенного слоя аутентификации, а не для прямого доступа из браузера.

Совместимость отката отдельно объявлена в `tool.omnicio.runtime.rollback_contract` файла `pyproject.toml`: `public-email-holdings-v1`. Перед восстановлением прежнего приложения deployer проверяет одинаковый известный контракт в статических метаданных обеих версий и доверенные права файлов. Старый Python для этой проверки не запускается. Версия 1.3.0 без такого контракта не становится допустимым откатом после появления email-аккаунтов и неизвестных оценок. При несовместимости приложение и наблюдатели останавливаются и отключаются; новая версия и её окружение сохраняются для проверенного восстановления. Неопределённый результат остановки сообщается отдельно. Если сбой произошёл до активации новой версии и текущая версия подтверждённо совместима, восстанавливаются только настройки окружения без перезапуска работающих служб. Повторная попытка получает свежее состояние под общей блокировкой развёртывания; неудачная загрузка не стирает данные предыдущей попытки. Ошибки перезапуска служб или восстановления nginx дают отдельный неуспешный результат. Этот механизм не заменяет восстановление базы и не даёт разрешения на миграцию.

Для инфраструктуры действует ранее принятый режим одной существующей базы `4215095`. Подготовленный контроллер 1.3.0 → 1.4.0 использует этот кластер и не создаёт резервных копий, экспортов, клонов или новых хранилищ. Исключение для исторического перехода 1.2.0 → 1.3.0 не расширяется: новый переход требует действительного подтверждения восстановления до остановки писателей и изменения схемы. Исторический переход продолжает проверяться по закреплённым исходным контрактам в `tests/fixtures/accepted_upgrade_1_3.json`; этот fixture не является новой инструкцией развёртывания.

Проверка существующего кластера использует его фактические ID, имя, тип PostgreSQL, регион, зону, признак управления и подключение к закрытой сети. Каталоги типов и тарифов для создания новых баз не участвуют в этом пути. Контроллер не меняет тариф или ресурсы кластера; действующие ограничения размера диска, автоматического расширения и расчётного объёма резервного хранения проверяются отдельно по фактическому состоянию. Этот расчёт не является подтверждением счёта провайдера.

Исходная установка закреплена в `tool.omnicio.timeweb.upgrade`: работающая 1.3.0 `a775679cc353eeb64fb51721fdd963eb660e5edb`, её schema contract и SHA-256 двух миграций. При несовпадении фактического приложения, базы, PostgreSQL 18, исходной схемы или её ограничений переход не начинается. Контроллер применяет ровно 0029–0030 в одной внешней транзакции; собственная обёртка 0029 снимается только после проверки digest, а 0030 передаётся без добавления вложенного COMMIT. Исторические 0001–0028 не исполняются повторно. SQL ограничен 30 секундами, ожидание блокировки — 5 секундами, транзакция — 60 секундами. Канонический readiness дополнительно проверяет реальные поля, типы, ограничения email, уникальность, внешние ключи, индексы и RLS, а не только имена таблиц и ограничений.

Подтверждение восстановления читается только на действующем сервере из существующих `/var/lib/omnicio-recovery/status.json`, `manifest.json` и `database.dump.encrypted`. Нужны подлинные HMAC-квитанции экспорта и проверенного изолированного восстановления, совпадающие кластер, исходный release и фактический PostgreSQL system identifier, все четыре проверки содержимого/схемы/внешних ключей/tenant isolation и возраст исходной копии не более 24 часов. Контроллер проверяет права файлов, фактически расшифровывает ограниченный по размеру архив в памяти и сверяет SHA-256 зашифрованных и расшифрованных данных. Ключи `OMNICIO_RESTORE_RECEIPT_KEY` и `OMNICIO_RESTORE_ARCHIVE_KEY` должны уже находиться в защищённой серверной конфигурации; публикация сохраняет их и не выводит в журнал. Наличие этих файлов, ключей и необходимого права прочитать system identifier должно быть подтверждено на сервере. Успешный тест с искусственным архивом или одна запись `verified` не заменяют эти доказательства.

До миграции и до изменения `product.env` проверяется эффективная конфигурация будущего приложения тем же сборщиком, который создаёт итоговый файл; сохраняются только предусмотренные интеграционные ключи. Оба workflow передают одинаковые настройки будущего приложения. Канонические проверки приложения подтверждают допустимость отправителя, выбранного ключа шифрования писем, настроенного push-ключа, лимита помощника, сессии и оператора. Проверка шифрует и расшифровывает только искусственную строку в памяти, не отправляет письма и не утверждает доставку. Замена существующих ключей восстановления в рамках обновления запрещена: она требует отдельной процедуры, сохраняющей доступ к архиву и подлинность квитанций. Перед публикацией проверяется критический путь включённой email-аутентификации, включая фактическую доставку проверочного письма. Общий рыночный источник используется только при подтверждённом разрешении на публичное распространение; если источник отсутствует или не разрешён, интерфейс показывает его недоступность, а остальные функции продолжают работать.

После принятия кода `Auth PostgreSQL` на push в `main` выполняет только `preflight`. Проверка читает действующую установку, идентичность базы, существующие доказательства восстановления и будущую конфигурацию. Результаты восстановления и конфигурации выводятся отдельно: ошибка одного не скрывает состояние другого. Этот режим не изменяет схему, файлы окружения или квитанции перехода и не останавливает службы. Доступ использует прежний проверенный SSH-путь, который при завершении пытается отвязать и удалить временный ключ. Успешный удалённый отчёт сам по себе не подтверждает результат этой очистки у провайдера.

Операторский отчёт `preflight` и `email_probe` содержит этапы проверки, признаки наличия эффективных настроек SMTP, отдельного рыночного токена и разрешения на распространение, а также существующих recovery-ключей. Не достигнутая проверка обозначается `null`, а не отсутствием настройки. Дополнительно выводятся только метаданные четырёх предусмотренных файлов, фактическое число CPU, объём и доступность памяти, свободное место и сведения об ОС действующего хоста. Эти наблюдения не заменяют чтение и проверку подлинности recovery proof, не меняют readiness и не доказывают доступность или права источника. Секреты, тела файлов и строки производственной БД в отчёт не попадают. Диагностика не добавляется в публичный API сайта.

Ручной `Auth PostgreSQL` принимает `operation=preflight`, `email_probe` или `apply`; значение по умолчанию — `preflight`. Для `email_probe` оператор явно задаёт разрешённого получателя через вход workflow. Отправка одного контрольного письма разрешена только для первой попытки такого запуска: используется действующий SMTP-транспорт сервера с будущими `AUTH_SMTP_*`, без очереди auth-заданий и без изменения аккаунта. В журнал попадают идентификатор сообщения и безопасный результат транспорта. Принятие SMTP-сервером не доказывает получение письма: перед выбором `apply` оператор проверяет и фиксирует поступление этого же `Message-ID` в разрешённый ящик. При неопределённом исходе отправка не повторяется автоматически; сначала проверяется почтовый ящик и уже созданный запуск. Ошибка recovery сама по себе не мешает этой разрешённой пробе, если подтверждены исходная установка, база и почтовая конфигурация.

Миграция запускается только явным `operation=apply` из принятого `main` после проверки восстановления и доставки. Она заново читает все обязательные доказательства и конфигурацию; прежний успешный `preflight` не заменяет проверку перед DDL. `Auth application deploy` публикует приложение только при отдельном ручном запуске из принятого `main`. Автоматического перехода от успешной проверки к публикации нет. Между COMMIT миграции и успешным запуском новой версии прежнее приложение остаётся остановленным, поэтому оба этапа выполняются в согласованное окно обновления.

Писатели останавливаются только после предварительных проверок, с сохранением их состояния в отдельной квитанции `/var/lib/omnicio-upgrade/1.4.0.json`; квитанция 1.3.0 сохраняется. Сбой до COMMIT допускает возобновление прежних служб только после повторного подтверждения исходной схемы и установки. После COMMIT или при неопределённом состоянии прежняя 1.3.0 остаётся остановленной. Повтор сверяет квитанцию и фактическую схему; успешный COMMIT не приводит к повторному DDL. Затем допускается только проверенный accepted main 1.4 или отдельно подтверждённое восстановление.

Этот код является подготовкой выпуска, а не подтверждением восстановления production. При отсутствии подходящих существующих доказательств переход остаётся закрыт. Действующий запрет на новые копии не снимается автоматически; получение новой recovery точки требует предметного решения владельца до изменения рабочей базы.

Изменения принимаются через PR. Для последнего head обязательны успешные проверки и Sonar без нерешённых или принятых замечаний по правилам `AGENTS.md`. Исключение для лимита строк анализа main не отменяет проверку PR. Перед выпуском проверяются происхождение exact main из принятого PR и совпадение trees, foundation/browser/PostgreSQL для этого SHA, действующий порядок перехода схемы, конфигурация интеграций и подтверждённая версия по HTTPS. Ошибка проверки не разрешает слепой откат схемы или удаление пользовательских данных.


## Проверка изменений

Применимые проверки действующего репозитория:

```bash
uv sync --frozen --all-extras --all-groups
uv run ruff check src tests .github/scripts
uv run mypy src
uv run pytest
node tests/i18n-contract.cjs
OMNICIO_PYTHON=.venv/bin/python node tests/frontend-smoke.cjs
```

Нативные PostgreSQL-проверки используют только изолированный тестовый PostgreSQL 18 и предусмотренные `OMNICIO_TEST_DATABASE_URL` / `OMNICIO_TEST_POSTGRES_BIN`, не production.
Принятые миграции не переписываются. Тесты поведения меняются вместе с соответствующим выпуском, а не отключаются ради новой документации.
Сквозные сценарии определены в критериях каждого выпуска; результаты относятся к проверенному commit и отдельно подтверждаются после публикации.
