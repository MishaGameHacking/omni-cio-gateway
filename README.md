# OMNICIO 1.4.0

OMNICIO — публичный сервис рыночного мониторинга с личным кабинетом для анализа текущего инвестиционного портфеля. Один общий серверный контур собирает доступные котировки, справочники и новости независимо от пользователей. Подключённый портфель сопоставляется с этими данными и выбранными пользователем условиями.

Этот репозиторий содержит приложение и проверяемый кандидат обновления. Наличие кода или успешного локального теста не подтверждает его публикацию на `omnicio.ru`, доступность SMTP или лицензию на распространение рыночных данных. Правила разработки и принятия изменений находятся в `AGENTS.md`.

## Изменения 1.4.0

- Регистрация по почте без квоты на число аккаунтов. Вход через VK ID и T-ID удалён из приложения и нового развёртывания.
- Отдельный пароль OMNICIO, подтверждение владения почтой восьмизначным кодом, повторная отправка, вход и восстановление пароля.
- Публичные каталог, котировки, карточки инструментов, новости и состояния общих источников доступны без пользовательского аккаунта или токена.
- Пользовательский T-Invest токен ограничен проверкой доступных счетов и чтением текущих позиций и денежных остатков. Отдельный серверный источник используется для рынка.
- Демонстрационный режим, брокерская история операций и runtime исполнения сделок удалены. Исторические принятые миграции сохранены; прежние записи не становятся публичными.
- Кабинет показывает текущую оценку, количество активов, деньги, распределение, выбранную стратегию и собственные снимки стоимости. Доходность счёта по недоступной истории не рассчитывается.

## Границы данных

| Контур | Источник и разрешённые данные | Доступ |
|---|---|---|
| Общий рынок | Отдельно настроенный серверный источник, каталог, цены, публичные новости и показатели | Открыт без аккаунта; фактическое покрытие и свежесть указаны |
| Аккаунт | Почта, Argon2id-хеш пароля, доказательство подтверждения, сессии и версии согласий | Только владелец; служебные данные не выдаются в публичные API |
| Личный портфель | Текущие инструменты, количество, блокировки, деньги и собственные снимки | Только владелец; серверное шифрование токена и FORCE RLS |
| Стратегия | Выбранный шаблон или параметры пользователя, ограничения, цели, результаты расчётов | Только владелец |
| Оплата и уведомления | Состояние собственной подписки, выбранные каналы и события сервиса | Отдельная функция аккаунта, не история брокера |

Почта и связанный с аккаунтом портфель являются пользовательскими данными. Доступ к портфелю по секретному токену не делает портфель общедоступным. Брокерский профиль, история покупок, пополнений и переводов не нужны приложению и не запрашиваются.

## Вход по почте

Допустимые домены: `gmail.com`, `mail.ru`, `xmail.ru`. Адрес нормализуется и проверяется сервером. Пароль отдельный от почтового; новый пароль имеет 15–128 символов, поддерживает Unicode и пробелы, проверяется по локальному списку очевидных слабых значений. Это не проверка полного внешнего реестра утечек.

На сервере хранится Argon2id PHC с индивидуальной случайной солью: 19 456 KiB памяти, два прохода, одна полоса. Исходный пароль не сохраняется и не отправляется в письме. Проверка почты не является многофакторной защитой последующих входов: обычный вход выполняется почтой и паролем.

Код содержит восемь цифр, действует десять минут, имеет пять попыток и потребляется атомарно. Повторная отправка возможна не раньше чем через 60 секунд и не сбрасывает ограничения перебора. Проверочное значение кода — HMAC с отдельным назначением существующего ключа; из одной копии базы нельзя перебрать короткий код без серверного ключа. Данные ожидающего письма зашифрованы в постоянной очереди PostgreSQL. Доставка повторяется ограниченно и учитывает актуальность задания. Истёкшие и завершённые задания очищаются.

Ограничения частоты учитывают почту и сетевой контекст, сохраняются в базе и не исчезают после перезапуска процесса. Ответы восстановления не раскрывают наличие адреса. Анонимный проверочный поток привязан к защищённой HttpOnly-cookie. Auth POST проверяют Origin. После восстановления пароля прежние сессии отзываются; открытая страница сразу очищает личные данные и ожидающие запросы, а другие вкладки получают сигнал завершения сессии. Вход повторяется с новым паролем.

### HTTP-контракт

| Маршрут | Назначение |
|---|---|
| `GET /api/auth/config` | Email-only режим, домены, длина пароля, версии документов и готовность доставки |
| `POST /api/auth/email/register` | Проверка полей и согласий; постановка письма в очередь |
| `POST /api/auth/email/verify` | Атомарное подтверждение кода и выдача защищённой сессии |
| `POST /api/auth/email/resend` | Ограниченная повторная отправка в текущем потоке |
| `POST /api/auth/email/login` | Почта и отдельный пароль OMNICIO |
| `POST /api/auth/email/password-reset/request` | Нейтральный ответ и письмо для подходящего адреса |
| `POST /api/auth/email/password-reset/confirm` | Однократный код и новый пароль; отзыв старых сессий |
| `POST /api/auth/email/enroll` | Привязка почты к тому же аккаунту из действующей сессии |

Существующие аккаунты не пересоздаются. Enrollment требует исходную действующую сессию и подтверждение её профиля; совпадение почты не объединяет аккаунты. После подтверждения карточка почты и список сессий загружаются заново; запоздавший ответ прежнего запроса не может вернуть старые сведения, а настройки и черновики того же владельца сохраняются. Обычный вход очищает предыдущий частный контекст до проверки новой сессии, в том числе при временном сбое этой проверки. После исчезновения всех прежних сессий оператор должен проверить принадлежность старого аккаунта отдельным согласованным процессом. Система не открывает старые портфели заявителю по одному адресу.

## T-Invest: только текущее состояние

Пользовательский транспорт работает только с production API и разрешает ровно три метода:

| Метод | Зачем он нужен |
|---|---|
| `UsersService.GetAccounts` | Технический выбор доступного счёта и проверка `accessLevel` |
| `OperationsService.GetPositions` | Текущие позиции, свободные и заблокированные количества, деньги |
| `OperationsService.GetWithdrawLimits` | Текущие денежные остатки и доступные ограничения, включая обеспечение |

Все возвращённые счета должны иметь `ACCOUNT_ACCESS_LEVEL_READ_ONLY`. Пустой список, неполные идентификаторы, `FULL_ACCESS`, `UNSPECIFIED` или `NO_ACCESS` отклоняются. Проверка выполняется при preview, сохранении и последующих обновлениях. При неизвестных правах доступ прекращается до исправления токена.

Официальный API описывает права на уровне доступного счёта. Это не глобальная криптографическая аттестация всех возможных скрытых прав токена: приложение проверяет доступную ему информацию и ограничивает собственный транспорт независимо от неё. Практически следует выпускать отдельный read-only токен для нужного счёта.

`GetAccounts` не предоставляет маску полей: лишние поля ответа отбрасываются при разборе. Технические поля для выбора счёта не переиспользуются для профиля человека. `GetPortfolio`, `GetInfo`, операции, брокерские отчёты, торговые и переводные методы в пользовательском контуре не вызываются. Вызов метода вне списка запрещается до сети. Источник общих цен использует иной credential и иной транспорт.

Количество позиции включает свободные и заблокированные единицы. Блокировка обозначается в инструментах, а не автоматически в лотах. Оценка по общей текущей цене учитывает её единицы и валюту; неподтверждённая оценка или денежный остаток — `null`, не ноль. Денежный остаток не заменяет брокерскую проверку покупательной способности конкретной сделки.

Торговые endpoints, исполнение плана, отмена и сверка брокерских заявок удалены. Отключение токена не пытается отменять реальные ранее размещённые заявки. Наличие старой записи исполнения не должно лишать владельца возможности отключить токен или удалить свои данные.

## Непрерывный общий рынок

`MarketService` запускает фоновые сборщики в lifespan приложения, даже если пользователей нет. Отдельные циклы собирают официальные показатели, новости, общий каталог/котировки, фундаментальные данные и новости инструментов. Сбой одного источника не должен останавливать остальные. Публичные запросы используют общий кэш и не инициируют чтение пользовательского токена.

Текущий runtime использует один процесс приложения, чтобы не дублировать сборщиков и кэши. Наблюдатель портфелей и прочие очереди работают отдельно от действий посетителя. Timeweb/systemd перезапускает процесс после отказа; при остановке сборщики завершаются ограниченно по времени. Общий рыночный кэш находится в памяти и наполняется заново после рестарта; личные снимки и очереди хранятся в PostgreSQL.

| Публичный API | Содержание |
|---|---|
| `/api/public/market-status` | Работа циклов, последнее наблюдение, возраст, ошибки и покрытие |
| `/api/public/market` | Постраничный общий каталог с ценой, свежестью и доступной оценкой риска |
| `/api/market/instruments/search` | Поиск инструментов без аккаунта |
| `/api/market/instruments/{uid}` | Общая карточка и биржевые свечи |
| `/api/market/instruments/{uid}/stream` | SSE общих обновлений, без контекста портфеля |
| `/api/market/quotes` | Общие котировки выбранных инструментов |
| `/api/news` | Общие новости с точной связью инструментов, пагинацией и указанием источника |

Поля `scope`, `coverage`, `observed_at`, `quote_time` и состояния источников обязательны для интерпретации. Изменение цены между серверными наблюдениями не выдаётся за изменение за торговый день. Отсутствие цены не означает нулевую стоимость; старое наблюдение не получает новое биржевое время. `real_time_guaranteed=false` и `all_internet=false` отражают реальные пределы покрытия.

Для масштабирования на несколько процессов или серверов потребуется выделить общий сборщик и долговечный общий кэш/хранилище, согласовать задания, нагрузку и лимиты поставщиков. Само увеличение числа веб-процессов не является таким масштабированием. Предел общего покрытия определяется доступными источниками и производительностью измеряемого конвейера, а не числом аккаунтов.

### Права на источники

Бесплатный API брокера для его клиента не равен бесплатной публичной ретрансляции. MOEX указывает условия распространения исходных и производных материалов, включая публикацию на сайтах. Обработка котировки не снимает автоматически требования источника. Поэтому общий брокерский источник требует отдельного серверного токена и подтверждённого основания для распространения. Пользовательские токены для этого не подходят и не используются.

Без настроенного и разрешённого общего источника интерфейс показывает его недоступность; приложение не подставляет примерные котировки и не объявляет ISS гарантированно мгновенным. Независимые официальные показатели и новости могут продолжать обновляться. Возможность бесплатного неограниченного публичного real-time потока не заявляется.

## Личный кабинет и расчёты

Внешний вид сохраняет исходный логотип, фон Земли, тёмную палитру, карточки, боковую навигацию и адаптивные экраны. Набор данных изменён под текущий контракт: нет демонстрационного баланса, доходности «с покупки» или фактической истории выплат. Общие карточки рынка доступны гостю; позиция, избранное и сохранение стратегии требуют аккаунта.

Стратегии используют текущий состав портфеля и подтверждённые общие данные. Версионные параметры, резерв, горизонт, ограничения концентрации и выбранный пользователем риск сохраняются отдельно от рыночных исходников. Недоступные финансовые факты дают неполный или неизвестный результат. В приложении нет полномочий совершить рассчитанную сделку.

Снимки стоимости показывают собственные наблюдения сервиса. Поле `value_change` означает разницу наблюдённых стоимостей; без истории денежных потоков это не инвестиционная доходность. Цели используют текущую долю портфеля либо сумму, введённую пользователем. Прежние цели с источником фактически полученных выплат показывают недоступный источник до изменения пользователем.

Публичные дивиденды, купоны и параметры инструмента относятся к рынку. Они не доказывают, что владелец портфеля получил выплату. Исторические модели исследования используют историю рыночного инструмента с ограничениями полноты, доступности на дату и валютных единиц; они не восстанавливают скрытую историю операций пользователя.

## Конфигурация и эксплуатация

| Переменные | Назначение |
|---|---|
| `DATABASE_URL` | Серверная PostgreSQL; секрет не выдаётся клиенту |
| `CLIENT_IP_KEY`, `BROKER_TOKEN_CRYPTO_KEY` | Защита проверочных значений и брокерских токенов |
| `AUTH_SMTP_HOST`, `AUTH_SMTP_PORT`, `AUTH_SMTP_USERNAME`, `AUTH_SMTP_PASSWORD`, `AUTH_SMTP_SENDER`, `AUTH_SMTP_MODE` | Доставка проверочных писем; TLS или STARTTLS, порт по умолчанию 465 |
| `MARKET_DATA_TOKEN` | Отдельный серверный источник рынка |
| `MARKET_DATA_DISTRIBUTION_APPROVED` | Явное подтверждение оператором прав на публичное использование; по умолчанию false |
| `LEGAL_OPERATOR_NAME`, `LEGAL_OPERATOR_EMAIL`, `LEGAL_*_VERSION` | Оператор, контакт и согласованные версии документов |
| `OPERATOR_USER_ID` | Явный серверный доступ к операторской сводке, без повышения роли из браузера |

Настройки SMTP не зависят от включения пользовательских уведомлений. Неполная SMTP-конфигурация блокирует отправку новых кодов; существующий вход паролем не должен зависеть от кратковременного сбоя почты. Проверка конфигурации не доказывает доставку в реальные ящики: перед публикацией требуется проверить отправителя, доставку и сообщения об ошибках без раскрытия секретов.

Общие параметры интерфейса находятся в `web/config.js`, переводы RU/EN — в `web/i18n.js`, маршруты и примитивы — в `web/workspace.js`, сетевые и пользовательские сценарии — в `web/app.js`. Цвета и токены оформления централизованы в `web/tokens.css`. `web_assets.py` формирует согласованную версию всех статических файлов; обновление PWA не должно подменять сохранённые данные аккаунта.

### Миграции и выпуск

Принятые SQL-миграции 0001–0028 остаются неизменными. `0029_email_auth.sql` добавляет почтовые идентичности, проверочные задания и постоянные ограничения частоты; `0030_portfolio_read_only.sql` допускает неизвестную текущую стоимость и денежные показатели. Прежние пользовательские записи не мигрируют по одному совпадению адреса.

Runtime и deployer проверяют общий контракт `schema.py`, включая таблицы, необходимые поля и принудительную изоляцию финансовых данных. В текущем Timeweb bootstrap миграции и приложение используют одного владельца таблиц `omnicio_app`; FORCE RLS сохраняется. Серверные auth-таблицы предназначены для доверенного слоя аутентификации, а не для прямого доступа из браузера.

Совместимость отката отдельно объявлена в `tool.omnicio.runtime.rollback_contract` файла `pyproject.toml`: `public-email-holdings-v1`. Перед восстановлением прежнего приложения deployer проверяет одинаковый известный контракт в статических метаданных обеих версий и доверенные права файлов. Старый Python для этой проверки не запускается. Версия 1.3.0 без такого контракта не становится допустимым откатом после появления email-аккаунтов и неизвестных оценок. При несовместимости приложение и наблюдатели останавливаются и отключаются; новая версия и её окружение сохраняются для проверенного восстановления. Неопределённый результат остановки сообщается отдельно. Если сбой произошёл до активации новой версии и текущая версия подтверждённо совместима, восстанавливаются только настройки окружения без перезапуска работающих служб. Повторная попытка получает свежее состояние под общей блокировкой развёртывания; неудачная загрузка не стирает данные предыдущей попытки. Ошибки перезапуска служб или восстановления nginx дают отдельный неуспешный результат. Этот механизм не заменяет восстановление базы и не даёт разрешения на миграцию.

Для инфраструктуры действует ранее принятый режим одной существующей базы `4215095`. Подготовленный контроллер 1.3.0 → 1.4.0 использует этот кластер и не создаёт резервных копий, экспортов, клонов или новых хранилищ. Исключение для исторического перехода 1.2.0 → 1.3.0 не расширяется: новый переход требует действительного подтверждения восстановления до остановки писателей и изменения схемы. Исторический переход продолжает проверяться по закреплённым исходным контрактам в `tests/fixtures/accepted_upgrade_1_3.json`; этот fixture не является новой инструкцией развёртывания.

Исходная установка закреплена в `tool.omnicio.timeweb.upgrade`: работающая 1.3.0 `a775679cc353eeb64fb51721fdd963eb660e5edb`, её schema contract и SHA-256 двух миграций. При несовпадении фактического приложения, базы, PostgreSQL 18, исходной схемы или её ограничений переход не начинается. Контроллер применяет ровно 0029–0030 в одной внешней транзакции; собственная обёртка 0029 снимается только после проверки digest, а 0030 передаётся без добавления вложенного COMMIT. Исторические 0001–0028 не исполняются повторно. SQL ограничен 30 секундами, ожидание блокировки — 5 секундами, транзакция — 60 секундами. Канонический readiness дополнительно проверяет реальные поля, типы, ограничения email, уникальность, внешние ключи, индексы и RLS, а не только имена таблиц и ограничений.

Подтверждение восстановления читается только на действующем сервере из существующих `/var/lib/omnicio-recovery/status.json`, `manifest.json` и `database.dump.encrypted`. Нужны подлинные HMAC-квитанции экспорта и проверенного изолированного восстановления, совпадающие кластер, исходный release и фактический PostgreSQL system identifier, все четыре проверки содержимого/схемы/внешних ключей/tenant isolation и возраст исходной копии не более 24 часов. Контроллер проверяет права файлов, фактически расшифровывает ограниченный по размеру архив в памяти и сверяет SHA-256 зашифрованных и расшифрованных данных. Ключи `OMNICIO_RESTORE_RECEIPT_KEY` и `OMNICIO_RESTORE_ARCHIVE_KEY` должны уже находиться в защищённой серверной конфигурации; публикация сохраняет их и не выводит в журнал. Наличие этих файлов, ключей и необходимого права прочитать system identifier должно быть подтверждено на сервере. Успешный тест с искусственным архивом или одна запись `verified` не заменяют эти доказательства.

До миграции и до изменения `product.env` проверяется эффективная конфигурация будущего приложения тем же сборщиком, который создаёт итоговый файл; сохраняются только предусмотренные интеграционные ключи. Оба workflow передают одинаковые настройки будущего приложения. Неполные или недопустимые настройки почты, сессии и оператора останавливают подготовку; проверка не отправляет письма и не утверждает доставку. Замена существующих ключей восстановления в рамках обновления запрещена: она требует отдельной процедуры, сохраняющей доступ к архиву и подлинность квитанций. Отсутствие разрешения на общий источник не включает его автоматически. Допуск к публикации требует отдельного фактического подтверждения SMTP-доставки и разрешённого рыночного источника.

Писатели останавливаются только после предварительных проверок, с сохранением их состояния в отдельной квитанции `/var/lib/omnicio-upgrade/1.4.0.json`; квитанция 1.3.0 сохраняется. Сбой до COMMIT допускает возобновление прежних служб только после повторного подтверждения исходной схемы и установки. После COMMIT или при неопределённом состоянии прежняя 1.3.0 остаётся остановленной. Повтор сверяет квитанцию и фактическую схему; успешный COMMIT не приводит к повторному DDL. Затем допускается только проверенный accepted main 1.4 или отдельно подтверждённое восстановление.

Этот код является подготовкой выпуска, а не подтверждением восстановления production. При отсутствии подходящих существующих доказательств переход остаётся закрыт. Действующий запрет на новые копии не снимается автоматически; получение новой recovery точки требует предметного решения владельца до изменения рабочей базы.

Изменения принимаются через PR. Для последнего head обязательны успешные проверки и Sonar без нерешённых или принятых замечаний по правилам `AGENTS.md`. Исключение для лимита строк анализа main не отменяет проверку PR. Перед выпуском проверяются происхождение exact main из принятого PR и совпадение trees, foundation/browser/PostgreSQL для этого SHA, действующий порядок перехода схемы, конфигурация интеграций и подтверждённая версия по HTTPS. Ошибка проверки не разрешает слепой откат схемы или удаление пользовательских данных.

## Проверка изменений

```bash
uv sync --frozen --all-extras --all-groups
uv run ruff check src tests .github/scripts
uv run mypy src
uv run pytest
node tests/i18n-contract.cjs
OMNICIO_PYTHON=.venv/bin/python node tests/frontend-smoke.cjs
```

Нативные PostgreSQL-тесты требуют отдельной одноразовой PostgreSQL 18, переменных `OMNICIO_TEST_DATABASE_URL` и при проверках восстановления `OMNICIO_TEST_POSTGRES_BIN`. Они не должны запускаться на производственной базе. Проверяются миграции на заполненных данных и повторное применение, ограниченная роль, FORCE RLS, подтверждение и перебор кода, конкурентная регистрация, отзыв сессий, восстановление пароля, изоляция портфелей и отсутствие чтений прежней истории. Искусственные значения допустимы только в тестовых фикстурах.

Browser-проверки используют production renderer, реальные HTTP-контракты и изолированные данные: гостевой рынок, email-вход, текущие позиции, сохранение стратегии, безопасные повторы, смену аккаунта, навигацию, графики и мобильную геометрию. Успешные проверки относятся к конкретной сборке; результаты PR и фактической публикации проверяются отдельно.
