# OMNICIO — Android и сервер Timeweb

Актуальное поручение владельца от **11.10.2026** заменяет прежний local-first/fixture этап.
Подготавливаемый Android 2.7.0 (`versionCode=10`) — нативный Kotlin/Compose клиент существующего HTTPS API `https://omnicio.ru`.
Брендовая иконка и applicationId сохранены. Деморежима нет ни в debug, ни в release.

## API без презентационного сайта

По последнему уточнению владельца от 11.10.2026 отдельный сайт о продукте больше не нужен. Сохраняются один Android-клиент и существующая инфраструктура Timeweb. Текущая публичная страница ещё работает на том же VDS; отдельная платная услуга для неё в этом изменении не заказывалась и не отменялась.

`https://omnicio.ru` пока остаётся адресом API приложения, OAuth callbacks и документов согласий. Его DNS, TLS и nginx нельзя удалять вместе с HTML-страницей. Вывод презентационного frontend и его публикации требует сохранить эти технические маршруты. Отдельный static-only workflow не заменяет guarded application deploy.

GitHub хранит исходники и сценарии сборки/развёртывания. Живые аккаунты, портфели и чаты хранятся в PostgreSQL; рабочие секреты не коммитятся. Обновление репозитория не доказывает развёртывание сервера.

Актуальные объём и разрывы — в `docs/system-plan.md` и `docs/ui-plan.md`. Текущая ветка не является опубликованным выпуском. Серверные email routes и SMTP-проверки ниже описывают пока действующий старый backend/deployer; их вывод из login-контракта остаётся задачей до приёмки. После отмены почтового входа отправлять новые проверочные письма не требуется.

## Архитектура

- Android предоставляет только Telegram и VK ID. Новый аккаунт создаётся сервером после согласий; второй способ привязывается из профиля. Почтовые формы и запросы клиента удалены.
- Только сессия сервера определяет пользователя; профиль и версия ответа проверяются повторно.
- Timeweb хранит портфель, историю, цели и события в существующем защищённом PostgreSQL.
- Приложение не сохраняет финансовые данные, пароли, broker credential или cookies на диск; ответы и сессия существуют в памяти процесса. После его завершения нужен новый вход.
- На устройстве сохраняются только тема и скрытие сумм; старые fixture preferences удаляются при переходе.
- Broker credential передаётся после согласия по HTTPS в существующий encrypted server boundary. Торговые действия отсутствуют.
- Числа приходят как точные decimal strings. Отсутствие данных не заменяется нулём.

## Интерфейс и фактические возможности

- **Обзор:** серверная стоимость, деньги, актуальность и интерактивная история наблюдений; периоды, выбор точки и доступный список значений. История стоимости не называется доходностью.
- **Портфель:** все переданные сервером позиции, поиск и подробности с источниками.
- **Помощник:** серверные события, отметка прочтения и загрузка следующих страниц.
- **Настройки:** тема, подключение read-only счёта, три стратегии и конструктор своей, серверная проверка ограничений счёта, цели и выход.
- Светлая/тёмная темы, векторные значки, подписи, крупные зоны нажатия, навигационная панель для широкого экрана.
- При ошибках отображается причина и возможность повтора. Неполные и устаревшие данные обозначаются явно. Отсутствующие источники не придумываются.

Покупка подписки исключена из текущего продукта. Нативный чат подключён к серверному API; модель в production пока не активирована. Помощник показывает историю диалога и события. Фоновые push-уведомления и автоматические торговые рекомендации этим клиентом не заявляются. В серверном коде сохранены существующие пользователи и миграции.

Запускать `ru.omnicio.app.debug`, отдельно от `ru.omnicio.app`.

### Android Studio: `INSTALL_FAILED_UPDATE_INCOMPATIBLE`

Эта ошибка означает, что APK уже собран, но установленный `ru.omnicio.app.debug` подписан другим ключом. Очистка Gradle, повторная сборка, `adb install -r` и увеличение версии не заменяют подпись. Для обновления с сохранением локальных данных нужен прежний debug keystore. Стандартное расположение в Windows — `%USERPROFILE%\.android\debug.keystore`; проверить используемый сертификат можно командой `.\gradlew.bat :app:signingReport`. Не удалять текущий ключ и не передавать keystore или его пароли в чат/GitHub. Для скачанного CI APK сравнить сертификат с `android-build.json` того же выпуска.

Если прежний ключ недоступен, Android требует удалить старый debug package перед новой установкой. Следующая команда удаляет **его локальные данные и настройки**, но не release `ru.omnicio.app` и не серверный аккаунт. Выполнять только после осознанного выбора переустановки:

```powershell
.\gradlew.bat :app:uninstallDebug :app:installDebug --no-configuration-cache
```

После `BUILD SUCCESSFUL` запустить **Run → app**, либо:

```powershell
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb shell dumpsys package ru.omnicio.app.debug | Select-String "versionName|versionCode"
& $adb shell monkey -p ru.omnicio.app.debug -c android.intent.category.LAUNCHER 1
```

Нельзя произвольно менять applicationId ради обхода подписи: сервер разрешает только зарегистрированные Android packages для Telegram/VK callbacks. Переустановка устраняет конфликт сертификатов, но доступность сервера проверяется отдельно.

Release-подпись хранится в защищённом окружении; debug APK не является выпуском RuStore. Подписанную сборку и работу на устройстве проверяют отдельно.

Для скачиваемого установочного файла запустить `Android CI` → `Run workflow` на accepted `main`. После обязательного main release gate, Android lint/unit/build и проверки APK-подписи workflow создаёт debug prerelease в [GitHub Releases](https://github.com/MishaGameHacking/omni-cio-gateway/releases). В нём находятся APK, `android-build.json` (версия, commit, SHA-256, сертификат, run) и `SHA256SUMS.txt`. При несовпадении сертификата с прежним debug APK Android не разрешит обновление поверх него; не удалять старую установку и данные автоматически. Подписанный магазинный выпуск по-прежнему требует защищённого release key и проверки на устройстве.

GitHub используется только бесплатно. Все jobs выполняются на четырёх существующих self-hosted Windows/X64 runner с label `omni-cio-ci`. Диагностика PostgreSQL, browser screenshots и PR APK сохраняются на выполнившем job runner в `%RUNNER_TOOL_CACHE%\omnicio-ci-evidence` на семь дней; точный путь, исходный SHA, результат и контрольные суммы опубликованы в job summary и run logs. Журнал полного набора тестов остаётся в Actions. Установочные файлы accepted main хранятся в Release assets, независимо от квоты Actions artifacts. Ошибка теста или сохранения обязательного evidence продолжает завершать job с ошибкой.

## Работа с интерфейсом в Android Studio

`MainActivity.kt` запускает Jetpack Compose, поэтому отдельного XML layout для Activity нет. В том же файле добавлены `@Preview` входа (светлая/тёмная темы) и пустых состояний Обзора, Портфеля и Помощника. Предпросмотр вызывает реальные экранные функции, без ViewModel, сетевых запросов и вымышленных финансовых значений.

1. Откройте весь корень репозитория с `settings.gradle.kts`, а не отдельный Kotlin-файл.
2. Выберите вариант `debug`, выполните **Sync Project with Gradle Files** и дождитесь завершения индексации.
3. Откройте `app/src/main/java/ru/omnicio/app/MainActivity.kt` и выберите **Split** или **Design** в редакторе.
4. Выполните **Build & Refresh** в панели Preview. Разметка редактируется в Compose-функциях внутри `ui/`; это не XML drag-and-drop редактор.
5. Для настоящего входа и серверных данных используйте **Run → app** на эмуляторе или телефоне. Редактор Preview не поддерживает сетевую авторизацию.

Добавление Preview не снимает требования exact-head CI и проверки на устройстве; рендер на ноутбуке владельца не заявляется проверенным удалённо.

## Конфигурация и эксплуатация

Операторское соединение помощника теперь поддерживает `ASSISTANT_PROVIDER=ollama` (прежний default) или `openai_compatible`. Для Timeweb AI Gateway официальный endpoint — `https://api.timeweb.ai/v1`; используются `ASSISTANT_BASE_URL`, `ASSISTANT_MODEL` с фактическим ID из каталога и защищённый `ASSISTANT_API_KEY`. `ASSISTANT_ENABLED` остаётся `false`, пока не приняты маршрут обработки персонального контекста, согласия и проверка соединения. Ключи не добавляются в APK или Git. Простое добавление GitHub variable не подтверждает настройку запущенного backend.

Android-помощник содержит диалог и отдельную ленту событий. Он получает историю, отправляет явные вопросы с серверным контекстом, показывает источники и проверяет незавершённую отправку без повторного запроса к модели. Каталог предлагает три подхода и собственную стратегию; Android сохраняет рабочие условия на сервере и запускает проверку счёта. Общий интернет-поиск, автоматические персональные торговые планы и production/recovery acceptance остаются открытыми.

| Переменные | Назначение |
|---|---|
| `DATABASE_URL` | Серверная PostgreSQL; секрет не выдаётся клиенту |
| `CLIENT_IP_KEY`, `BROKER_TOKEN_CRYPTO_KEY` | Защита проверочных значений и брокерских токенов |
| `AUTH_SMTP_HOST`, `AUTH_SMTP_PORT`, `AUTH_SMTP_USERNAME`, `AUTH_SMTP_PASSWORD`, `AUTH_SMTP_SENDER`, `AUTH_SMTP_MODE` | Доставка проверочных писем; TLS или STARTTLS, порт по умолчанию 465 |
| `MARKET_DATA_TOKEN` | Отдельный серверный источник рынка |
| `MARKET_DATA_DISTRIBUTION_APPROVED` | Явное подтверждение оператором прав на публичное использование; по умолчанию false |
| `LEGAL_OPERATOR_NAME`, `LEGAL_OPERATOR_EMAIL`, `LEGAL_*_VERSION` | Оператор, контакт и согласованные версии документов |
| `OPERATOR_USER_ID` | Явный серверный доступ к операторской сводке, без повышения роли из браузера |

Настройки SMTP не зависят от включения пользовательских уведомлений. Неполная SMTP-конфигурация блокирует отправку новых кодов; существующий вход паролем не должен зависеть от кратковременного сбоя почты. Проверка конфигурации не доказывает доставку в реальные ящики: перед публикацией требуется проверить отправителя, доставку и сообщения об ошибках без раскрытия секретов.

Общие параметры интерфейса находятся в `web/config.js`, переводы RU/EN — в `web/i18n.js`, маршруты и примитивы — в `web/workspace.js`, сетевые и пользовательские сценарии — в `web/app.js`. Цвета и токены оформления централизованы в `web/tokens.css`. `web_assets.py` формирует согласованную версию всех статических файлов; обновление PWA не должно подменять сохранённые данные аккаунта.

### Миграции и выпуск

Принятые SQL-миграции 0001–0028 остаются неизменными. `0029_email_auth.sql` добавляет почтовые идентичности, проверочные задания и постоянные ограничения частоты; `0030_portfolio_read_only.sql` допускает неизвестную текущую стоимость и денежные показатели. Прежние пользовательские записи не мигрируют по одному совпадению адреса.

Runtime и deployer проверяют общий контракт `schema.py`, включая таблицы, необходимые поля и принудительную изоляцию финансовых данных. В текущем Timeweb bootstrap миграции и приложение используют одного владельца таблиц `omnicio_app`; FORCE RLS сохраняется. Серверные auth-таблицы предназначены для доверенного слоя аутентификации, а не для прямого доступа из браузера.

Совместимость отката отдельно объявлена в `tool.omnicio.runtime.rollback_contract` файла `pyproject.toml`: `public-email-holdings-v1`. Перед восстановлением прежнего приложения deployer проверяет одинаковый известный контракт в статических метаданных обеих версий и доверенные права файлов. Старый Python для этой проверки не запускается. Версия 1.3.0 без такого контракта не становится допустимым откатом после появления email-аккаунтов и неизвестных оценок. При несовместимости приложение и наблюдатели останавливаются и отключаются; новая версия и её окружение сохраняются для проверенного восстановления. Неопределённый результат остановки сообщается отдельно. Если сбой произошёл до активации новой версии и текущая версия подтверждённо совместима, восстанавливаются только настройки окружения без перезапуска работающих служб. Повторная попытка получает свежее состояние под общей блокировкой развёртывания; неудачная загрузка не стирает данные предыдущей попытки. Ошибки перезапуска служб или восстановления nginx дают отдельный неуспешный результат. Этот механизм не заменяет восстановление базы и не даёт разрешения на миграцию.

Для инфраструктуры действует ранее принятый режим одной существующей базы `4215095`. Подготовленный контроллер 1.3.0 → 1.4.0 использует этот кластер и не создаёт резервных копий, экспортов, клонов или новых хранилищ. Исключение для исторического перехода 1.2.0 → 1.3.0 не расширяется: новый переход требует действительного подтверждения восстановления до остановки писателей и изменения схемы. Исторический переход продолжает проверяться по закреплённым исходным контрактам в `tests/fixtures/accepted_upgrade_1_3.json`; этот fixture не является новой инструкцией развёртывания.

Проверка существующего кластера использует его фактические ID, имя, тип PostgreSQL, регион, зону, признак управления и подключение к закрытой сети. Каталоги типов и тарифов для создания новых баз не участвуют в этом пути. Контроллер не меняет тариф или ресурсы кластера; действующие ограничения размера диска, автоматического расширения и расчётного объёма резервного хранения проверяются отдельно по фактическому состоянию. Этот расчёт не является подтверждением счёта провайдера.

Исходная установка закреплена в `tool.omnicio.timeweb.upgrade`: работающая 1.3.0 `a775679cc353eeb64fb51721fdd963eb660e5edb`, её schema contract и SHA-256 двух миграций. При несовпадении фактического приложения, базы, PostgreSQL 18, исходной схемы или её ограничений переход не начинается. Контроллер применяет ровно 0029–0030 в одной внешней транзакции; собственная обёртка 0029 снимается только после проверки digest, а 0030 передаётся без добавления вложенного COMMIT. Исторические 0001–0028 не исполняются повторно. SQL ограничен 30 секундами, ожидание блокировки — 5 секундами, транзакция — 60 секундами. Канонический readiness дополнительно проверяет реальные поля, типы, ограничения email, уникальность, внешние ключи, индексы и RLS, а не только имена таблиц и ограничений.

Подтверждение восстановления читается только на действующем сервере из существующих `/var/lib/omnicio-recovery/status.json`, `manifest.json` и `database.dump.encrypted`. Нужны подлинные HMAC-квитанции экспорта и проверенного изолированного восстановления, совпадающие кластер, исходный release и фактический PostgreSQL system identifier, все четыре проверки содержимого/схемы/внешних ключей/tenant isolation и возраст исходной копии не более 24 часов. Контроллер проверяет права файлов, фактически расшифровывает ограниченный по размеру архив в памяти и сверяет SHA-256 зашифрованных и расшифрованных данных. Ключи `OMNICIO_RESTORE_RECEIPT_KEY` и `OMNICIO_RESTORE_ARCHIVE_KEY` создаёт разрешённый ручной on-host recovery в защищённой серверной конфигурации, сохраняя существующие ключи; публикация сохраняет их и не выводит в журнал. Наличие этих файлов, ключей и необходимого права прочитать system identifier должно быть подтверждено на сервере. Успешный тест с искусственным архивом или одна запись `verified` не заменяют эти доказательства.

До миграции и до изменения `product.env` проверяется эффективная конфигурация будущего приложения тем же сборщиком, который создаёт итоговый файл; сохраняются только предусмотренные интеграционные ключи. Оба workflow передают одинаковые настройки будущего приложения. Канонические проверки приложения подтверждают допустимость отправителя, выбранного ключа шифрования писем, настроенного push-ключа, лимита помощника, сессии и оператора. Проверка шифрует и расшифровывает только искусственную строку в памяти, не отправляет письма и не утверждает доставку. Замена существующих ключей восстановления в рамках обновления запрещена: она требует отдельной процедуры, сохраняющей доступ к архиву и подлинность квитанций. Перед публикацией проверяется критический путь включённой email-аутентификации, включая фактическую доставку проверочного письма. Общий рыночный источник используется только при подтверждённом разрешении на публичное распространение; если источник отсутствует или не разрешён, интерфейс показывает его недоступность, а остальные функции продолжают работать.

После принятия кода `Auth PostgreSQL` на push в `main` выполняет только `preflight`. Проверка читает действующую установку, идентичность базы, существующие доказательства восстановления и будущую конфигурацию. Результаты восстановления и конфигурации выводятся отдельно: ошибка одного не скрывает состояние другого. Этот режим не изменяет схему, файлы окружения или квитанции перехода и не останавливает службы. Доступ использует прежний проверенный SSH-путь, который при завершении пытается отвязать и удалить временный ключ. Успешный удалённый отчёт сам по себе не подтверждает результат этой очистки у провайдера.

Операторский отчёт `preflight` и `email_probe` содержит этапы проверки, признаки наличия эффективных настроек SMTP, отдельного рыночного токена и разрешения на распространение, а также существующих recovery-ключей. Не достигнутая проверка обозначается `null`, а не отсутствием настройки. Дополнительно выводятся только метаданные четырёх предусмотренных файлов, фактическое число CPU, объём и доступность памяти, свободное место и сведения об ОС действующего хоста. Эти наблюдения не заменяют чтение и проверку подлинности recovery proof, не меняют readiness и не доказывают доступность или права источника. Секреты, тела файлов и строки производственной БД в отчёт не попадают. Диагностика не добавляется в публичный API сайта.

Ручной `Auth PostgreSQL` принимает `operation=preflight`, `email_probe` или `apply`; значение по умолчанию — `preflight`. Для `email_probe` оператор явно задаёт разрешённого получателя через вход workflow. Отправка одного контрольного письма разрешена только для первой попытки такого запуска: используется действующий SMTP-транспорт сервера с будущими `AUTH_SMTP_*`, без очереди auth-заданий и без изменения аккаунта. В журнал попадают идентификатор сообщения и безопасный результат транспорта. Принятие SMTP-сервером не доказывает получение письма: перед выбором `apply` оператор проверяет и фиксирует поступление этого же `Message-ID` в разрешённый ящик. При неопределённом исходе отправка не повторяется автоматически; сначала проверяется почтовый ящик и уже созданный запуск. Ошибка recovery сама по себе не мешает этой разрешённой пробе, если подтверждены исходная установка, база и почтовая конфигурация.

Миграция запускается только явным `operation=apply` из принятого `main` после проверки восстановления и доставки. Она заново читает все обязательные доказательства и конфигурацию; прежний успешный `preflight` не заменяет проверку перед DDL. `Auth application deploy` публикует приложение только при отдельном ручном запуске из принятого `main`. Автоматического перехода от успешной проверки к публикации нет. Между COMMIT миграции и успешным запуском новой версии прежнее приложение остаётся остановленным, поэтому оба этапа выполняются в согласованное окно обновления.

Писатели останавливаются только после предварительных проверок, с сохранением их состояния в отдельной квитанции `/var/lib/omnicio-upgrade/1.4.0.json`; квитанция 1.3.0 сохраняется. Сбой до COMMIT допускает возобновление прежних служб только после повторного подтверждения исходной схемы и установки. После COMMIT или при неопределённом состоянии прежняя 1.3.0 остаётся остановленной. Повтор сверяет квитанцию и фактическую схему; успешный COMMIT не приводит к повторному DDL. Затем допускается только проверенный accepted main 1.4 или отдельно подтверждённое восстановление.

Этот код является подготовкой выпуска, а не подтверждением восстановления production. При отсутствии подходящих существующих доказательств переход остаётся закрыт. Владелец 11.10.2026 разрешил резервный архив и временную проверку восстановления без постоянного клона базы или сервера. Для этого в `Auth PostgreSQL` вручную выбирается `restore_drill=true`: проверенный код выполняется на существующем VDS, создаёт локальные ключи при их отсутствии, сохраняет зашифрованный архив и сверяет временное восстановление. Данные и ключи не поступают в GitHub Actions. После успешного удаления временной базы устанавливаются архив, манифест и подписанное подтверждение именно действующей исходной версии. Затем отдельно запускается `operation=preflight`. Доступ к production остаётся read-only; политики RLS не отключаются. На сервере при необходимости устанавливаются PostgreSQL 18 из подписанного PGDG-репозитория без постоянного локального кластера. Требуются прежние 192 МиБ доступной памяти и 1 ГиБ свободного диска. При нехватке только памяти оператор сохраняет закрытую квитанцию состояния и временно останавливает только службы OMNICIO, сохраняя их автозапуск. После работы, включая ошибку, службы возвращаются только после проверки исходной схемы, роли и установленной версии. Если процесс был принудительно прерван, следующий запуск сначала проверяет и завершает прежнее обслуживание. Нехватка диска не вызывает остановку приложения. В GitHub поступают только проверенные этап, категория ошибки и показатели ресурсов; ошибка продолжает завершать workflow неуспешно. Неподтверждённое восстановление не открывает переход схемы.

Изменения принимаются через PR. Для последнего head обязательны успешные проверки и Sonar без нерешённых или принятых замечаний по правилам `AGENTS.md`. Исключение для лимита строк анализа main не отменяет проверку PR. Перед выпуском проверяются происхождение exact main из принятого PR и совпадение trees, foundation/browser/PostgreSQL для этого SHA, действующий порядок перехода схемы, конфигурация интеграций и подтверждённая версия по HTTPS. Ошибка проверки не разрешает слепой откат схемы или удаление пользовательских данных.

### Telegram, VK ID и почта в Android 2.7

Серверная интеграция использует `TELEGRAM_CLIENT_ID` (GitHub Variable),
`TELEGRAM_CLIENT_SECRET` (GitHub Secret) и существующий `VKID_APP_ID` (Variable).
Client ID и Secret Telegram берутся в BotFather → бот OMNICIO → Login Widget;
для Telegram оставить алгоритм подписи RS256. Бот не получает доступ к перепискам,
не отправляет сообщения и не запрашивает номер телефона.

В разрешённых URL провайдеров зарегистрировать точные HTTPS-адреса:

- Telegram: `https://omnicio.ru/api/auth/social/telegram/callback`
- VK ID: `https://omnicio.ru/api/auth/social/vkid/callback`

Android открывает браузер провайдера. После подтверждения ссылка возвращает в
`ru.omnicio.app://auth` или `ru.omnicio.app.debug://auth` без кода/сессии в URL.
Самостоятельный запуск deep link не авторизует пользователя. Приложение завершает
одноразовый поток через свой cookie, существующий только в памяти.

Для почты нужны `AUTH_SMTP_HOST`, `AUTH_SMTP_PORT`, `AUTH_SMTP_SENDER`, `AUTH_SMTP_MODE`
в Variables и `AUTH_SMTP_USERNAME`, `AUTH_SMTP_PASSWORD` в Secrets. Подтверждение
и восстановление не работают без реальной доставки. Для существующих пользователей
VK сохраняются идентификатор профиля и портфель. Другие способы подключаются из
«Настройки → Способы входа» после недавнего входа. Автоматического слияния нет.

Проверять на устройстве: первый и повторный вход каждым способом, отказ провайдера,
возврат после поворота/сворачивания, истечение 10 минут, привязка из своего профиля,
конфликт чужой привязки, восстановление почтового пароля и отзыв других сессий.
Ключи и production-учётные данные в APK не входят. Публичный выпуск требует
конфигурации провайдеров, проверенного восстановления существующей БД и живого
прохождения этих сценариев; успешный CI сам по себе этого не подтверждает.
