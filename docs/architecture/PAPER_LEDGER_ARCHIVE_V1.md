# Paper Ledger Archive V1

## Purpose

PR-32 adds a storage-agnostic persistence boundary for the deterministic paper
account ledger. It provides canonical serialization, authenticated records,
hash chaining and strict restoration without adding a database, filesystem
writer or real-trading surface.

The archive is for paper state only. Every record preserves:

- `paper_only=true`;
- `broker_order_created=false`;
- `execution_ready=false`;
- `trading_methods=false`.

## Record format

`PaperLedgerArchiveRecordV1` contains:

- format and canonicalization versions;
- monotonically increasing sequence;
- UTC seal timestamp;
- non-secret key identifier;
- masked account identifier;
- currency and event count;
- previous-record digest;
- ledger SHA-256 digest;
- record SHA-256 digest;
- HMAC-SHA256 authentication tag;
- full typed `PaperAccountLedgerV1` snapshot.

The secret HMAC key is never serialized into the record.

## Canonicalization

Records use deterministic JSON:

- UTF-8;
- sorted object keys;
- compact separators;
- no NaN or Infinity;
- Pydantic JSON-mode values for Decimal and datetime fields.

The decoder rejects:

- invalid UTF-8;
- malformed JSON;
- duplicate JSON object keys;
- non-object roots;
- oversized records;
- fields outside the strict contract.

## Integrity and authentication

Three checks are distinct:

1. `ledger_digest` detects changes to the typed ledger payload.
2. `record_digest` binds metadata, chain pointer and ledger digest to the record.
3. `authentication_tag` proves possession of the externally supplied HMAC key.

A plain SHA-256 digest is not treated as proof of authenticity. The record model
therefore states `authentication_required=true`; only
`verify_paper_ledger_record` or `verify_paper_ledger_archive_chain` returns an
authenticated record.

Signing keys must contain at least 32 bytes. Keys are supplied by the caller and
are not stored, logged or generated by this module. Key rotation is supported
through `key_id` and a caller-provided key mapping during chain verification.

## Hash chain

The first record points to the all-zero genesis digest. Every later record must
point to the prior record digest.

Chain verification requires:

- contiguous sequences beginning at 1;
- a valid HMAC key for every key ID;
- exact previous-digest links;
- non-regressing seal timestamps;
- one masked account and one currency;
- unchanged initial paper cash and positions;
- non-regressing ledger timestamps;
- previous events and scenario IDs as an exact prefix of the next snapshot.

This detects history truncation and rewriting even when an attacker creates a
new internally valid ledger snapshot. Protection still depends on retaining a
trusted HMAC key and trusted genesis/latest digest outside the untrusted archive.

## Storage boundary

This PR does not:

- choose a filesystem path;
- write files;
- create a database;
- configure retention or backups;
- encrypt records at rest;
- distribute or rotate secret keys;
- implement concurrent writers.

`storage_backend_attached=false` is part of every record. A future adapter may
persist serialized bytes only after encryption, retention, locking, recovery
and secret-management requirements are designed and reviewed.

## Recovery

A caller restores state by:

1. loading ordered serialized records from its storage backend;
2. supplying the HMAC keys by key ID;
3. verifying the complete chain;
4. using the ledger from the returned latest record.

No state is restored from an unverified parse result.

## Validation

Focused tests cover:

- deterministic seal/serialize/verify round trips;
- wrong keys and modified HMAC tags;
- ledger and record digest tampering;
- duplicate JSON keys and invalid UTF-8;
- explicit unverified parsing semantics;
- full-chain recovery and key rotation;
- missing keys and broken links;
- history rewrite and truncation;
- sequence and time regressions;
- weak keys, empty chains and execution-flag tampering.

Regression Shield must pass lock verification, repository policy, compile,
Ruff, formatting, mypy, stable entrypoint, read-only release contract, full
pytest with coverage, dependency audit, Bandit and secret scanning.

## Rollback

Revert the PR merge commit. The deterministic in-memory paper ledger and all
public gateway behavior remain unchanged.
