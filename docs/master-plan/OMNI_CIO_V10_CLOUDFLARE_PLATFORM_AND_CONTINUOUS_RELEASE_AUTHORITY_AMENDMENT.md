# Omni-CIO V10 — Cloudflare Platform & Continuous Release Authority Amendment

Status: **OWNER-APPROVED GOVERNANCE CHANGE / EFFECTIVE ONLY WHEN ACCEPTED ON PROTECTED `main`**

Decision date: **2026-08-29**

Machine-readable companion:

`../architecture/V10_CLOUDFLARE_PLATFORM_AUTHORITY_CONTRACT.json`

This amendment records the OWNER correction that Omni-CIO V10 must use GitHub as the canonical engineering source of truth and Cloudflare Workers Paid as the primary managed application/edge/build platform for new V10 work. It supersedes conflicting current/future provider-selection wording without rewriting historical acceptance evidence.

## 1. Authority order

1. **GitHub is authority rank 1** for source, protected `main`, Pull Requests, review evidence, exact commit identity, release provenance and accepted engineering state.
2. **Cloudflare Workers Paid is platform rank 2** for new V10 application hosting, edge delivery, managed deployment, eligible hosted verification and platform services.
3. A Cloudflare dashboard state, deployment, build, preview, AI output or external provider state never overrides accepted GitHub source/review/provenance authority.
4. Project/product identity remains `OmniCIOUserAccount -> Tenant -> server-side Session`; Cloudflare identity/access controls are infrastructure/security controls and may not mint or select a product tenant.

## 2. Provider authority transition

For **new V10 runtime/deployment/release work** after this amendment is accepted:

- `CLOUDFLARE_WORKERS_PAID` is the selected primary managed platform target;
- Cloud.ru Evolution is no longer the selected target for new V10 deployment work;
- Render.com is no longer an active new-V10 deployment, attestation, hosted-release-alignment or recovery target;
- no new Render mutation, `RENDER_ZERO_CHARGE_ATTESTATION` refresh or Render-based release acceptance may be required by current V10 work;
- accepted WP22A Render + Neon evidence remains immutable historical technical/synthetic evidence and must not be rewritten as if it never happened;
- protected V9 Render production/recovery baseline remains protected, including the stable `app:app` entrypoint, until an explicit later V9 decommission/recovery decision changes it.

Historical contracts, runbooks and acceptance evidence may retain the provider names that were true at the time. They are not current provider authority when they conflict with this amendment.

## 3. This governance change is not a production cutover

Acceptance of this amendment by itself performs **no**:

- Cloudflare Worker/Pages deployment;
- DNS or domain mutation;
- WAF/Access/Turnstile policy mutation;
- Cloudflare API-token or secret creation;
- Neon mutation or migration;
- Telegram/VK provider registration or secret provisioning;
- public-user activation;
- `PUBLIC_MULTI_USER_ENABLED=true` transition;
- broker credential provisioning;
- broker submit, trading or Real-money authority change.

Provider/runtime mutation and production cutover remain mandatory split boundaries under Amendment 12.

## 4. Continuous exact-main public release law

Omni-CIO V10 is an evolving engineering program. The public Omni-CIO product must not wait for the whole V10 program to reach 100% before completed capabilities can be released.

For each accepted repository change:

1. a new squash-merged protected `main` SHA becomes the source identity of a new product revision candidate;
2. merge alone does **not** immediately authorize production traffic;
3. all required exact-main post-merge gates must actually reach terminal `success`;
4. a Cloudflare immutable candidate version may then be built/uploaded against that exact accepted SHA;
5. candidate acceptance must prove exact SHA/release identity, health, security and applicable capability gates;
6. production promotion occurs only after those gates pass;
7. after successful promotion, the public deployed source SHA must converge to the latest accepted promotable `main` SHA;
8. if a newer `main` is not promotable, production remains on the last-known-good version and the system must expose an explicit `UPDATE_PENDING` or `DEPLOYMENT_BLOCKED/OUT_OF_SYNC` state instead of pretending alignment;
9. rollback may restore a previous known-good Cloudflare Worker version, but rollback does not rewrite GitHub authority or make the older source the new canonical `main`.

The release pipeline must re-check current `main` immediately before promotion. A superseded candidate must never be promoted merely because it passed checks earlier.

## 5. Product release identity

Public release identity is generated by the accepted release event and must **not** require a source-code version-bump commit that would itself create another SHA.

Required public identity fields:

- `product_release` — CalVer-style `YYYY.MM.DD.N`;
- `source_sha` — exact accepted GitHub commit;
- `cloudflare_version_id` — immutable Cloudflare Worker version identity when applicable;
- `released_at_utc`;
- `release_status`;
- compatible schema/migration level where stateful resources are involved.

Engineering V10 program tags/percentages and public product release identifiers are separate concepts.

The canonical Web/API health/version surface must make deployed source identity observable without exposing secrets or private tenant data.

## 6. One canonical public product

The target remains one canonical public Omni-CIO Web product and one canonical product identity/session/tenant stack.

Cloudflare may provide:

- Workers and Static Assets;
- Workers Builds;
- Custom Domains, DNS and TLS;
- WAF/DDoS/rate controls;
- Turnstile for supported abuse-sensitive browser actions;
- Access for private/admin/engineering surfaces;
- Hyperdrive only after database compatibility proof;
- KV/R2/Durable Objects/Queues/Workflows when an owning package proves a concrete need;
- Workers AI/Vectorize only when the AI/Cortex package is authorized.

These services may not create a second Gateway, second Web product, parallel product-auth stack, competing database authority, competing scheduler or competing broker/execution stack.

## 7. Web and runtime migration preference

The existing V10 Web remains the product source. The migration preference remains:

`REUSE_AS_IS > WRAP_ADAPTER > EXTRACT_TO_CORE > REWRITE_REQUIRED > RETIRE`.

Current approved Cloudflare target investigation:

- existing React/Vite Web -> Workers Static Assets / Workers-compatible Vite path after repository integration evidence;
- existing FastAPI backend -> Python Workers only after exact dependency/runtime compatibility evidence;
- no assumption that CPython/native dependencies such as `psycopg[binary]`, broker SDK/runtime dependencies or socket expectations work unchanged in the Python Workers/Pyodide environment;
- no rewrite merely to claim Cloudflare adoption;
- if a required component is incompatible, the owning runtime-compatibility change must choose an accepted Cloudflare-compatible adapter/runtime boundary or explicitly prove why the component must remain elsewhere while preserving one canonical product.

## 8. PostgreSQL / Neon / Hyperdrive boundary

The accepted PostgreSQL/Neon tenant/RLS data authority is preserved by this governance amendment.

- no automatic D1 replacement of the financial/tenant truth store;
- PostgreSQL 18 compatibility remains an evidence requirement;
- Hyperdrive must not be assumed compatible with PostgreSQL 18 merely because it supports PostgreSQL generally;
- any Hyperdrive adoption requires a focused compatibility/recovery/transaction/RLS test before mutation;
- tenant scope, server-side authorization, RLS/FORCE-RLS, backup/restore and cross-tenant negatives remain mandatory.

## 9. Cloudflare security layer is additive

The target public request path is conceptually:

`Internet -> Cloudflare DNS/TLS/DDoS/WAF/rate/Turnstile as applicable -> product authentication/authorization -> Tenant -> PostgreSQL RLS -> tenant-scoped provider/broker state`.

Cloudflare Access is appropriate for private/admin/engineering surfaces. It is not a replacement for Telegram Login / VK ID product authentication and is not sufficient proof of multi-user tenant isolation.

Secrets must use approved secret custody and must never be placed in repository source, PR comments, CI logs, screenshots or release manifests.

## 10. Workers Builds Paid capacity law

The OWNER already has an active Workers Paid subscription. The currently documented Workers Builds paid-plan reference values at this decision are:

- `6000` included build minutes/month;
- up to `6` concurrent builds/account;
- `20` minute build timeout;
- `4` vCPU/build;
- `8 GB` memory/build;
- `20 GB` disk/build.

These values are **mutable external facts** and must be revalidated against current official Cloudflare documentation before a material CI/cost/configuration mutation.

The existing subscription authorizes use of included Workers Paid capacity for Omni-CIO. It does **not** authorize uncontrolled paid overage or a higher paid plan. Automatic paid fallback/overage beyond the already-authorized subscription baseline is forbidden without an explicit fresh OWNER cost decision.

Repository CI routing does not change merely because this amendment is accepted. Until the dedicated Cloudflare Builds verifier integration is accepted, existing GitHub/Lenovo routing remains authoritative.

## 11. Verification topology target

The migration target is work-conserving parallel verification:

- portable Web/Python/governance/security/build checks should migrate to Cloudflare Workers Builds where semantics are equivalent and the 20-minute build boundary is respected;
- independent shards should use build-watch paths/caching where safe to avoid wasting paid-plan capacity;
- Windows-, PowerShell-, ACL-, PostgreSQL-18-native or other genuinely Windows-specific contracts stay on trusted Lenovo self-hosted runners until a later accepted change proves equivalent semantics elsewhere;
- multiple Lenovo runner services may increase concurrency only with isolated work directories/resources and deterministic collision testing;
- a quota, provider outage or missing runner is never converted into fake `success`;
- GitHub remains the canonical check/review/provenance surface even when Cloudflare performs compute.

## 12. Cloudflare resource authority boundaries

Cloudflare platform services are available when an owning package justifies them:

- KV — edge configuration/cache/ephemeral metadata, not financial truth;
- R2 — appropriate blob/export/report/recovery-artifact storage, not tenant ledger authority;
- Durable Objects — coordination/stateful edge primitives only where single-instance consistency is actually required;
- Queues/Workflows — bounded background delivery, retry and durable orchestration when the owning subsystem reaches that stage;
- Workers AI/Vectorize — only inside authorized AI/Cortex scope and never as financial/broker authority.

No platform feature is adopted merely because the subscription includes it.

## 13. Capability activation remains progressive and fail-closed

Amendment 13 remains active:

- completed capabilities need not wait for final `V10.0.0`;
- Telegram Login, VK ID and multi-user access may become `LIVE_OPERABLE` only after their own real-provider/runtime/privacy/security/capacity/monitoring gates;
- `PUBLIC_MULTI_USER_ENABLED=false` remains the current runtime state until that capability's activation gate passes;
- Cloudflare deployment by itself does not activate real users.

## 14. Financial authority remains independent

This amendment never changes:

- broker write OFF;
- `trading_methods=false`;
- `REAL_TRADING_ENABLED=false`;
- transfer/withdrawal/margin/leverage/uncovered-short prohibition;
- requirement for later `REAL_MONEY_AUTHORIZED` evidence before real broker submit.

A merge, Cloudflare deployment, public release or user registration is never broker-submit authorization.

## 15. Mandatory implementation sequence

Because provider/security authority, runtime compatibility and production cutover are mandatory split boundaries, the accepted implementation order after this governance change is:

1. **`CLOUDFLARE-BUILDS-VERIFIER-INTEGRATION`** — repository-side Workers Builds configuration, portable verification shards, check/provenance integration and cost/timeout guards; **no production deploy**.
2. **`CLOUDFLARE-RUNTIME-COMPATIBILITY`** — React/Vite deployment configuration plus backend/dependency/PostgreSQL/Hyperdrive compatibility evidence; still no assumption of public-user activation.
3. **`CLOUDFLARE-CANDIDATE-DEPLOYMENT`** — provider mutation and immutable candidate deployment only after the prior exact-main gates pass.
4. **`CLOUDFLARE-PUBLIC-CUTOVER`** — canonical domain/DNS/TLS/security/promotion/rollback and capability-specific live-user activation evidence as a separate cutover change.

The already prepared `WEB-VISUAL-INTEGRATED` product update remains valid product scope but is not executed inside this provider/security authority change. WP23+ remains locked.

## Acceptance law

This amendment becomes current authority only after its focused PR completes:

1. cheap/focused preflight and full diff review;
2. all applicable exact-head DRAFT checks with conclusion `success`;
3. independent code/security review and zero unresolved blocking threads;
4. fresh unchanged-head READY checks with conclusion `success`;
5. squash merge;
6. exact-new-main Regression Shield plus applicable post-merge governance checks with conclusion `success`.

Until that chain completes, protected `main` remains authoritative and no Cloudflare production/provider mutation is implied.
