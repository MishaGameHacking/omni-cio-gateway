# Обязательное обновление и расчётный анализ портфеля

## Статус и границы

Сверка исходников: **17.10.2026**. Единый updater уже подключён к приложению;
это описание действующих модулей, а не невыпущенной ветки времён 0.5.1.
Актуальная версия, проверенный GitHub Release, доставка на Timeweb и незакрытые
пункты F01/F11/F14/F22/F23 указаны в [PLAN_STATUS.md](PLAN_STATUS.md).
Текущая поддержка — Android 15+ (`minSdk=35`, compile/target 36).

APK с блокирующим стартовым экраном требует готовой `/client/update-policy`
и проверенного файла на московском сервере. Обычный
[Timeweb deploy](../.github/workflows/timeweb-backend.yml) остаётся приостановленным;
отдельная доставка через московский workflow описана ниже. Статус публикации
не подтверждает новые инвестиционные алгоритмы, платные модели или проверку
на физическом телефоне. Секреты и пользовательские портфели не нужны тестам.

## Как действует обновление

- Рабочие API-клиенты передают `X-Analyst-Package` и `X-Analyst-Version-Code`. Ответ HTTP 426 сразу закрывает рабочее содержимое.
- При запуске, возвращении на передний план и затем раз в минуту открытое приложение
  получает политику с первого сервера. Без подтверждения актуальности содержимое
  не создаётся: фоновые эффекты экранов не продолжают опрашивать портфель.
- Поддерживается ровно опубликованный versionCode. Слишком новый неизвестный APK
  не вызывает понижение версии. Неверный package, неподдерживаемый Android и
  недоступный сервер имеют отдельное поведение. Нет скрытой кнопки обхода.
- Пользователь может закрыть приложение; блокировка не ограничивает телефон.
- По явному нажатию «Обновить» скачивается APK только с BASE_URL приложения, без
  переадресаций на сторонние адреса. Есть прогресс, предел размера и времени,
  проверка свободного места, размера, SHA-256, package, versionCode, minSdk и
  текущего сертификата подписи. После сбоя частичный файл удаляется; старое
  приложение и его данные не удаляются.
- Android PackageInstaller устанавливает только проверенное обновление самого
  приложения. Используется разрешённый self-update режим без лишнего подтверждения
  там, где ОС его допускает. STATUS_PENDING_USER_ACTION всегда обрабатывается.
  Разрешение устанавливать из этого источника и подтверждение Android могут быть
  обязательны. Никаких root, Accessibility, device-owner обходов или отключения
  Play Protect нет.
- ОС может завершить процесс при замене. Автоматический запуск из фона не
  форсируется. Предусмотрено уведомление «Открыть», если оно разрешено; иначе
  обычный запуск значком или кнопкой системного установщика. Нельзя обещать
  абсолютно бесшумную установку и открытие на любом телефоне.

## Совместимость клиента и независимое наблюдение

`backend/client_updates.py` добавляет публичную политику и APK-маршрут, а также
защищённый `/client/ready`. Проверка сессии предшествует проверке версии.
При включённом серверном enforcement (`ANDROID_UPDATES_ENABLED=true`)
неизвестный/старый клиент получает HTTP 426, но не теряет сессию и токен брокера.

С подэтапа F11.1 серверный сбор портфеля, история и базовые риск-проверки
не требуют актуального APK или действующего Android-сеанса. Обновление клиента
и недоступность APK-канала не останавливают серверное наблюдение.

Фоновое задание связано с конкретным брокерским подключением пользователя.
Отключение или замена токена проверяется до обработки, перед моделью и внутри
транзакций сохранения снимков, истории и карточек. Уже отправленный сетевой
запрос нельзя отменить задним числом, но его устаревший результат не публикуется.
Бюджет ИИ и разрешение внешней обработки остаются отдельными обязательными условиями.

При включённом enforcement совместимость проверяется для каждого API-запроса.
Старое устройство не отключает обновлённое. Заголовок версии — механизм совместимости,
а не подтверждение личности или криптографическая аттестация APK.

`ANDROID_UPDATES_ENABLED=false` отключает серверное требование актуального
versionCode для защищённых API до подготовленного перехода. Флаг **не отключает
`MandatoryUpdateHost` в Android**: этот стартовый экран всё равно проверяет
публичную политику. Поэтому одного выключенного enforcement недостаточно,
чтобы безопасно выпустить APK с отсутствующим или устаревшим манифестом.
Жизненный цикл серверного наблюдения остаётся независимым от обоих механизмов.

## Публикация без ловушки обновления

`release_publication.publish` — локальная операция доверенного выпуска, а не
HTTP API. Требуется отчёт проверок preview APK: чистая установка и запуск на
API 35 и 36, обновление и запуск после обновления на API 36. Для выпуска 0.10.0
исходный APK для обновления — опубликованный
0.9.0 / 33: он не поддерживает API 35, поэтому чистая установка на Android 15
не считается проверкой обновления. Полный контракт — в
[APK_INSTALLATION.md](APK_INSTALLATION.md).

`installation_evidence.py` привязывает записи установки и запуска preview
к SHA-256 проверяемого APK. UI проверяется на API 35 и 36 в отдельном
debug fixture из того же коммита; его тестовая Activity не входит в preview.
JSON-отчёт является контрактом доверенного CI/оператора, не независимой
криптографической аттестацией и не проверкой самообновления через UI на телефоне.

1. Собрать APK с тем же package и сертификатом, с большим versionCode. Выполнить
   apksigner, zipalign, установку, обновление и запуск по действующей матрице.
2. Подготовить каталог `ANDROID_RELEASE_DIR/<package>/` на нашем российском
   сервере, принадлежащий доверенному издателю. Backend получает только чтение.
3. Передать именно проверенные байты и отчёт. Файл именуется по версии и хешу.
   Сначала записывается полный APK, затем атомарно заменяется `current.json`.
   Нельзя отдельно увеличить минимальную версию без доступного файла.
4. Проверить HTTPS-политику и скачанный обратно APK, и лишь затем разрешить
   серверное enforcement при выполнении отдельных условий его включения.
5. Не переиспользовать номер версии с другим файлом, не понижать versionCode и
   не менять сертификат. Ошибочный выпуск исправлять новым, большим номером.
   Старые APK не удаляются этой библиотекой.

В `release_publication.py` файл и манифест fsync-ятся до замены; каталог и
файловая система должны иметь проверенный эксплуатационный режим.
Межхостовая транзакционная публикация и полный автоматический откат канала
не реализованы.

### Штатная доставка уже опубликованного APK на Timeweb

[repair-moscow-update-channel.yml](../.github/workflows/repair-moscow-update-channel.yml)
запускается вручную либо маркером `[repair-update-channel]` в коммите `main`,
попадающем под фильтры workflow. Проверенные идентификаторы Release, APK и
`apk-verification.json` должны совпадать в workflow и
[run_moscow_update_channel_repair.py](../.github/scripts/run_moscow_update_channel_repair.py).
Перед сетевым доступом выполняются проверки скриптов и `--check`.

Этот путь скачивает **существующие опубликованные байты**, проверяет их хеши,
передаёт APK/отчёт на московский сервер и сверяет локальный и публичный канал.
Для повторной доставки опубликованного 0.10.0 / 34 не нужно запускать
`android-apk.yml` и пересобирать новые байты под тем же versionCode.

Скрипт также заменяет **весь backend из текущего checkout**, а не только файл
APK. Перед запуском требуется проверить серверный diff этого коммита и его CI.
Он сохраняет копии прежнего backend и `backend.env`; рабочую SQLite-базу этот
путь не заменяет. Настройка `ANDROID_UPDATES_ENABLED=false` сохраняет отдельный
контроль условий включения серверного enforcement.

У rollback есть конкретная граница: удалённый trap восстанавливает backend и
`backend.env`, но **не возвращает прежний `current.json` канала**. Публичная
проверка скачивания выполняется уже после завершения этого удалённого trap.
Поэтому провал публичного read-back нельзя описывать как автоматически
отменённую публикацию. До новой попытки необходимо сверить фактический backend,
манифест и доступные APK и выбрать согласованное восстановление; старый APK
не следует объявлять текущим одним текстовым исправлением статуса.

### Однократный переход со старых APK

0.5.1 и более старые сборки не содержат этого updater. Их нельзя научить новому
экрану изменением одного сервера: после жёсткого запрета они лишь получат отказ
API. Сначала нужно один раз установить первую версию с updater. Только версии,
уже содержащие этот механизм, смогут затем обновляться сами с нашего сервера.
Не объявлять совместимость со «всеми любыми APK» задним числом.

## Расчётная часть: реализовано, но ещё не подключено к живому подбору

`backend/portfolio_risk.py` — исследовательское ядро без сетевых и торговых вызовов.
Его функции проверки покупки и сокращения не подключены как готовый план
к `/analysis/ideas` или `/analysis/research` и не выдают синтетические данные
в рабочую ленту. Текущий `/analysis/research` использует `risk_math.py` при
полных проверенных входах; его охват и ограничения описаны в
[RISK_REBALANCING.md](RISK_REBALANCING.md). Наличие нескольких математических
модулей не означает завершённого общего оптимизатора.

- Объединение по настоящему эмитенту, отрасли, классу, валюте и группе рейтинга.
  `company = название инструмента` и `assetUid` нельзя автоматически считать
  надёжным идентификатором всей компании. Входные позиции нужно заранее объединить
  по UID со всех счетов и оценить в одной валюте. Производные, фонды без состава,
  шорты, неизвестные оценки не получают фиктивной цены или диверсификации.
- Рейтинг хранится вместе с агентством, шкалой, датой, отзывом, источником и
  калибровкой. Национальный AAA не превращается в международный AAA. Просроченный
  рейтинг относится к неизвестным. PD и возврат после дефолта не генерируются
  из букв рейтинга: нужна документированная калибровка на соответствующий срок.
  Условный ожидаемый кредитный убыток = позиция × PD × (1 − recovery).
- Эмпирические VaR и Expected Shortfall считают потери по совместным, синхронным
  сценариям; дробная граница хвоста учитывается. Недостаток редких наблюдений
  обозначается явно. Доходности должны включать необходимые выплаты и валютную
  оценку; независимые случайные ряды вместо связанного рынка не подставляются.
- Блочный bootstrap совместных доходностей сохраняет зависимости внутри блока.
  Симуляция buy-and-hold допускает дрейф долей, а не бесплатную ежедневную
  ребалансировку. Выдаются частота пересечения порога капитала и 95%-интервал
  Уилсона для статистики симуляции. Это НЕ истинная вероятность банкротства
  и НЕ интервал всех возможных ошибок рыночной модели. Ноль событий не равен
  нулевому риску. Есть предел вычислений, параметры и seed воспроизводимы.
- По проверенным данным отчётности вычисляются долговая нагрузка, покрытие
  процентов и соотношение денежного потока с прибылью. Неположительная EBITDA,
  отсутствующие поля и банки требуют отдельного рассмотрения, а не деления на
  ноль или выдачи ложного благополучия.
- Предложения уменьшения доли учитывают компанию, лоты, заблокированные бумаги,
  доступность продажи и оценку комиссии. Недостижимое точное выравнивание и
  неизвестные налоги обозначаются. Это консервативная проверка превышений,
  не глобальный оптимизатор портфеля.
- Проверка покупки одного нового лота учитывает цену и комиссию, свободные
  деньги сверх резерва, компанию, сектор, класс, группу рейтинга, PD на срок,
  размер сделки и ликвидность. Все ограничения передаются явно. Прохождение
  фильтра НЕ означает «лучший из всех активов» и не заменяет анализ бизнеса.

## Переход к брокеру и понятные объяснения

В карточке существующей позиции доступны открытие официального HTTPS-адреса
инструмента и копирование тикера/ISIN. `BrokerInstrumentActions` ищет обработчик
ссылки, отличный от браузера; исследовательская карточка `PortfolioResearchPanel`
сначала адресует её `ru.tinkoff.investing`. При неудаче предлагается официальная
веб-страница или поиск по идентификаторам.
Не используется выдуманная custom-scheme и не гарантируется обработка ссылки
каждой версией Т‑Инвестиций. Переход никогда не создаёт покупку или продажу.

Расчётные объяснения формулируются через портфель пользователя: доля компании,
ограничение, что предлагается изменить, на сколько лотов, какие данные и расходы
ещё нужно проверить. «Избежать банкротства при любых обстоятельствах» не обещается.

## Ещё требуется

Живые лицензированные рейтинги и отчётность, нормализация эмитентов, корпоративные
действия и история полной доходности, новости и отраслевые связи, тест вне выборки,
сравнение кандидатов и многокритериальная оптимизация, пользовательский интерфейс
такого плана и end-to-end проверка самообновления на физическом телефоне.
Публикации APK и проверенные московские доставки уже есть в журнале выпусков;
их нельзя подменять утверждением, что на телефоне пройден весь сценарий. Резервные модели и источники не включены
покупкой дополнительных сервисов.
