12 — TELEGRAM COMPANION v4.0.1

Purpose
-------
Telegram Companion is a separate read-only interface to the existing Omni-CIO Gateway. It does not replace Custom GPT and does not share ChatGPT conversation history. Both interfaces call the same protected gateway.

Architecture
------------
Telegram user -> Telegram Bot API -> telegram_bot.app:app -> Omni-CIO Gateway -> T-Invest API

The Telegram service is deployed separately from the gateway so that a Telegram outage cannot break the main API. Use `render.telegram.yaml`; do not change the gateway start command `app:app`.

Security invariants
-------------------
- Telegram commands are read-only.
- `trading_methods=false`.
- No order placement, replacement, cancellation, stop order, or submission command exists.
- The webhook requires `X-Telegram-Bot-Api-Secret-Token` and compares it with `TELEGRAM_WEBHOOK_SECRET`.
- Only private chats are accepted.
- Only IDs from `TELEGRAM_ALLOWED_USER_IDS` may call the gateway.
- Telegram updates are deduplicated by `update_id`.
- Per-user requests are rate limited.
- Gateway calls use Bearer `OMNI_GATEWAY_API_KEY` and GET only.
- Tokens, API keys, raw Authorization headers, and full account IDs must never be logged or returned.
- Account identifiers are masked again before Telegram output.
- Automatic retries are allowed only for GET requests and temporary connection/HTTP failures.
- Permanent authorization and validation errors must not be retried.

Commands
--------
/help
/status
/health
/connection
/portfolio
/cash
/analytics
/operations [days]
/report
/report_status [task_id]

`/status` confirms the Telegram delivery path, then checks Gateway `/health` and T-Invest `/connection` using read-only GET requests.

`/report` starts a 31-day official T-Invest report with `wait_seconds=0`. When the gateway returns `pending`, the task ID is cached in memory for convenience and is also shown to the user. `/report_status` reuses the cached task ID or accepts an explicit ID. In-memory task IDs can be lost after a service restart, so the user-visible task ID remains the recovery mechanism.

Friendly output
---------------
Telegram v4.0.1 no longer sends full gateway JSON for normal commands. It selects a small, documented set of safe fields and formats money using the currency returned by the gateway. It must not recalculate, reinterpret, merge currencies, hide `complete=false`, or upgrade partial data to complete data.

Large messages are split below the Telegram Bot API text limit and labelled by part. The split operation must not expose additional fields or secrets.

Reliability
-----------
Free Render services can sleep after inactivity. For retryable Gateway failures the bot:

1. sends a short notice that the main server is waking;
2. repeats the same GET request according to the configured retry policy;
3. never converts a failed request into `ok`;
4. returns a friendly error if all attempts fail.

Retry environment variables:
- `TELEGRAM_GATEWAY_RETRY_ATTEMPTS` — additional attempts after the first request;
- `TELEGRAM_GATEWAY_RETRY_DELAY_SECONDS` — base delay before retries.

Automatic setup
---------------
On startup, when configuration is complete and `TELEGRAM_AUTO_CONFIGURE=true`, the service calls Telegram `getMe`, `setMyCommands`, and `setWebhook`. The webhook URL is derived from `TELEGRAM_PUBLIC_BASE_URL` or Render's `RENDER_EXTERNAL_URL`. Setup failures do not expose secrets; `/health` returns a degraded bootstrap status.

Required environment variables
------------------------------
TELEGRAM_BOT_TOKEN
TELEGRAM_WEBHOOK_SECRET
TELEGRAM_ALLOWED_USER_IDS
OMNI_GATEWAY_URL
OMNI_GATEWAY_API_KEY (or fallback GATEWAY_API_KEY)

Optional settings
-----------------
TELEGRAM_AUTO_CONFIGURE
TELEGRAM_PUBLIC_BASE_URL
TELEGRAM_REQUEST_TIMEOUT_SECONDS
TELEGRAM_GATEWAY_RETRY_ATTEMPTS
TELEGRAM_GATEWAY_RETRY_DELAY_SECONDS
TELEGRAM_MAX_RESPONSE_CHARS
TELEGRAM_MIN_REQUEST_INTERVAL_SECONDS

Versioning
----------
System release: v4.0.1 Telegram Reliability & Friendly Output.
Gateway API component remains v3.9.1 until its own public contract changes.
Telegram service health reports version 4.0.1 and entrypoint `telegram_bot.app:app`.

Testing
-------
Tests must use fake Telegram and gateway clients. No test may contact Telegram, Render, or T-Invest. Required cases: health without secrets, startup webhook setup, invalid webhook secret, unauthorized user, GET-only gateway command, `/status`, retryable and non-retryable failures, friendly output, safe message splitting, report task reuse, duplicate update suppression, and `trading_methods=false`.
