15 — DATA QUALITY SHADOW VALIDATION

Status: PR-06 implementation rules.

1. Scope

The current portfolio market dictionary is validated against
PortfolioSnapshotV1 after it is produced and before the established route
returns it. Shadow validation must not modify the dictionary, Action schema,
operationId, HTTP method, account access or broker calls.

2. Read-only invariants

- trading_methods=false remains mandatory.
- No order, replacement, cancellation, stop-order, transfer or withdrawal
  method is added or called.
- Gateway Actions remain GET-only.
- Render entrypoint remains app:app.

3. Shadow states

READY
- contract validation succeeded;
- quality=verified;
- completeness=complete;
- no warning/error DataIssue;
- arithmetic and identity checks in the adapter passed.

PARTIAL
- contract validation succeeded;
- the snapshot is incomplete, degraded or contains a blocking quality issue;
- it may be displayed with uncertainty;
- it must not be used by a future recommendation or execution workflow without
  a new verified snapshot.

REJECTED
- the source cannot satisfy contract v1;
- the current read-only response remains unchanged during shadow rollout;
- all future decision/trading workflows must fail closed.

4. Decision gate

Every future Decision Engine, rebalancing, preview orchestration or execution
flow that consumes PortfolioSnapshotV1 must call
require_portfolio_decision_ready before producing an actionable result.

The gate must reject PARTIAL and REJECTED snapshots. It must not infer or repair
missing identity, price, currency, lot, totals or account masking.

5. Safe diagnostics

Allowed log fields:
- schema name/version;
- status;
- decision_ready;
- quality/completeness;
- counts of issues, warnings, positions, cash balances and currencies;
- fixed error code;
- exception class name.

Forbidden log data:
- account ID, including masked ID;
- instrument identifiers or names;
- quantities, prices, cash and totals;
- raw payload;
- validation exception text;
- tokens, headers or credentials.

6. Compatibility

PR-06 does not publish the shadow result in the Action response. Public contract
changes require a separate migration PR and GPT/OpenAPI update.

7. Tests

Tests must prove:
- verified data becomes READY;
- partial data is blocked by the decision gate;
- rejected data fails closed;
- unexpected validator failures do not break the current read-only response;
- source payload is not mutated;
- wrapper preserves response object identity and is idempotent;
- sensitive values never appear in shadow logs.

8. Next step

PR-07 creates normalized operations and cash-flow contracts. Those contracts
must reuse provenance, Decimal money, quality/completeness and the same
fail-closed decision-gate semantics.
