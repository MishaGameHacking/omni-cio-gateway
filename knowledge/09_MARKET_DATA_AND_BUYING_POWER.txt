# 09 — MARKET DATA AND BUYING POWER

Назначение: правила для Omni-CIO при работе с текущими котировками, стаканом,
макроисточниками и расчётом покупательной способности. Этот документ не даёт
торговых полномочий. Шлюз остаётся read-only.

## 1. Источники и приоритет

1. Для счёта, денег, лимита вывода и позиций использовать только ответы gateway-методов getConnection, getPortfolioSnapshot и getEnrichedPortfolioSnapshot.
2. Для идентификации инструмента использовать findInstrument. Для расчёта по конкретной бумаге выбирать точное совпадение по ticker/UID и проверять instrument_type, class_code, lot, api_trade_available_flag.
3. Для текущих рыночных данных и execution-style расчёта использовать getMarketSnapshot по точному instrument_uid.
4. Для ключевой ставки использовать только typed snapshot официального источника Банка России `DailyInfo.KeyRateXML` после contract validation.
5. Публичный `MoexIssTqbrQuoteSnapshotV1` допускается только как независимый информационный источник/сверка для акций режима TQBR. Он не заменяет broker gateway quote и не считается гарантированно real-time.
6. Web Search использовать только для внешних фактов и новостей. Не подменять им данные брокерского счёта, стакана, котировки gateway, typed CBR snapshot или typed MOEX snapshot.
7. Если источники расходятся, не усреднять значения. Явно показать расхождение, время каждого источника и не делать уверенный вывод.

## 2. Обязательная идентификация инструмента

Перед рыночным расчётом проверить:
- название;
- ticker;
- ISIN;
- FIGI;
- instrument_uid;
- position_uid, если доступен;
- instrument_type;
- class_code;
- размер лота;
- api_trade_available_flag.

Не считать тикер уникальным без проверки UID и class_code. Для SBER не смешивать обычную акцию SBER и привилегированную SBERP.

## 3. Как трактовать рыночные данные

- last_price — цена последней зарегистрированной сделки. Это справочная цена, а не гарантированная цена покупки.
- best_ask — ближайшая видимая цена продажи. Для предварительного расчёта покупки использовать best_ask, если он доступен и свежий.
- best_bid — ближайшая видимая цена покупки.
- spread_absolute = best_ask - best_bid.
- spread_percent_of_midpoint = spread_absolute / ((best_ask + best_bid) / 2) * 100.
- quantity_lots в стакане — количество лотов, а не отдельных бумаг.
- api_trade_available_flag, limit_order_available_flag и market_order_available_flag описывают доступность через API, но не гарантируют ликвидность, исполнение или неизменность цены.

Всегда показывать retrieved_at и age_seconds для last_price/order_book, когда поля доступны.

## 4. Расчёт стоимости лота

Для акций и большинства инструментов с расчётной базой price_times_lot:
- стоимость_одного_лота = best_ask * lot.

Если best_ask отсутствует:
- допускается справочный расчёт по last_price * lot;
- расчёт пометить как менее надёжный;
- не называть его исполнимой стоимостью покупки.

Для облигаций не применять формулу акции автоматически. Учитывать процент от номинала, НКД и валюту только по данным gateway. Если нужных данных нет, написать: «Недостаточно данных для корректного расчёта полной стоимости лота облигации».

## 5. Покупательная способность

Рубли в портфеле и лимит вывода показывать раздельно. Лимит вывода не считать автоматически деньгами, доступными для покупки.

Для предварительного расчёта по акции:
- cash_rub = рублёвый денежный баланс из getPortfolioSnapshot;
- lot_cost = best_ask * lot;
- max_lots = floor(cash_rub / lot_cost);
- estimated_total = max_lots * lot_cost;
- cash_remainder = cash_rub - estimated_total.

Если max_lots = 0, сообщить, что по текущему best_ask целый лот не помещается в указанный рублёвый баланс.

Перед итогом проверить:
- cash_rub >= 0;
- best_ask > 0;
- lot >= 1;
- валюта инструмента соответствует валюте расчёта;
- данные не устарели критически;
- инструмент определён однозначно.

## 6. Что не включено в предварительный расчёт

Если gateway не вернул точные значения, отдельно перечислить, что не учтено:
- брокерская комиссия;
- биржевая комиссия;
- изменение best_ask до момента заявки;
- проскальзывание;
- частичное исполнение;
- блокировки и фактическая доступность денег;
- валютная конвертация;
- налоги и иные списания.

Не выдумывать тариф и комиссию. Не уменьшать баланс на приблизительную комиссию без явной просьбы пользователя и подтверждённого тарифа.

## 7. Стандартный порядок вызовов для теста покупательной способности

Если пользователь просит расчёт по тикеру и не задаёт другой порядок:
1. getPortfolioSnapshot.
2. findInstrument с instrument_type и api_trade_available_only=true.
3. Проверить точное совпадение и выбрать UID нужного инструмента.
4. getMarketSnapshot по выбранному UID, обычно depth=10.
5. Выполнить расчёты только из полученных данных.

Не вызывать getOperationsHistory, если пользователь не просил историю, комиссии или сверку операций.

## 8. Формат ответа

Показывать:
1. Маскированный счёт.
2. Рубли в портфеле.
3. Лимит вывода отдельно.
4. Идентификацию инструмента и размер лота.
5. Последнюю цену и возраст.
6. Best bid.
7. Best ask.
8. Спред в рублях и процентах.
9. Стоимость одного лота по best ask.
10. Максимальное целое количество лотов.
11. Расчётную стоимость этого количества.
12. Остаток рублей.
13. Торговый статус и флаги доступности.
14. Что не учтено.
15. Явную пометку: «Расчёт предварительный; заявка не создавалась и не отправлялась».

## 9. Уверенность и остановка

Высокая уверенность допустима только когда:
- счёт и рублёвый баланс получены успешно;
- инструмент найден однозначно;
- UID совпадает;
- market snapshot имеет status=ok или все нужные компоненты успешны;
- best_ask доступен;
- валюта и лот подтверждены;
- формулы показаны и арифметика проверена.

Остановить расчёт и запросить уточнение или повторный снимок, если:
- найдено несколько равнозначных инструментов;
- отсутствует best_ask;
- валюта не совпадает;
- данные заметно устарели;
- gateway вернул partial/error по критическому компоненту;
- баланс или идентификаторы противоречат друг другу.

## 10. Безопасность

- Не размещать, не заменять и не отменять заявки.
- Не просить и не показывать полный номер счёта, токен T-Invest или GATEWAY_API_KEY.
- Не утверждать, что покупка гарантированно исполнится.
- Не выдавать справочную цену за исполнимую.
- Рекомендации по покупке давать только по прямой просьбе пользователя и отдельно от фактического расчёта.

## 11. Ключевая ставка Банка России

- Источник истины — только `CbrKeyRateSnapshotV1` со статусом `available`, authority=`official` и source_id=`DailyInfo.KeyRateXML`.
- Текущее значение — последняя по effective_date запись внутри проверенного диапазона, а не число из web snippet или текста новости.
- `effective_date` показывает дату вступления ставки в силу; `retrieved_at` показывает, когда официальный источник был проверен. Эти даты не взаимозаменяемы.
- Decimal comma/point нормализуются в Decimal; float для ставки не использовать.
- При `unavailable`, stale cache или contract mismatch показывать «Данные Банка России недоступны»/прочерк с безопасным error code. Не переносить последнее известное значение без явного cache/freshness контракта.
- Не хранить сырой SOAP/XML, fault text или exception text.
- Ключевая ставка является макрофактом и не разрешает сделку, не заменяет market snapshot и не меняет `trading_methods=false`.

## 12. Cache и freshness ключевой ставки

- Использовать только `CbrKeyRateCacheResultV1`; не читать process-local cache напрямую.
- Cache identity включает точный диапазон `requested_from + requested_to`. Нельзя использовать snapshot другого диапазона.
- `fresh` разрешает показ значения. Всегда показывать `effective_date`, `retrieved_at` и `age_seconds`, если UI/owner поддерживает эти поля.
- Неудачный force refresh при ещё свежем cache допускает показ прежнего значения только как `fresh`, `served_from_cache=true`, `refresh_succeeded=false` и с безопасным refresh error code.
- После fresh TTL значение считается stale. Показ stale разрешён только при explicit trusted policy `allow_stale=true`; обязательно визуально отметить stale и возраст.
- Без explicit stale policy возвращать `unavailable`, даже если stale snapshot физически ещё хранится.
- После stale TTL entry удаляется и не может быть показан.
- Не подменять unavailable значением из web search, текста новости или предыдущего процесса.
- Cache очищается при restart; наличие прежнего значения не гарантируется.
- Fresh/stale timestamps ключевой ставки не объединять с датами брокерского счёта, портфеля или рыночного стакана.
- Cache не даёт торговых полномочий и не меняет `trading_methods=false`.

## 13. Публичная котировка MOEX ISS TQBR

- Принимать только `MoexIssTqbrQuoteSnapshotV1` с точной identity `MOEX:TQBR:{SECID}` и source authority=`official`.
- Источник ограничен акциями режима `TQBR`; нельзя автоматически применять его к облигациям, фондам, фьючерсам, валютам или другому board.
- `public_unauthenticated_feed=true`, `delayed_data_possible=true`, `realtime_guaranteed=false` и `informational_use_only=true` являются обязательными ограничениями, а не декоративными флагами.
- Всегда различать `quote.as_of` и `retrieved_at`; возраст рассчитывать от `quote.as_of`, а не от момента HTTP-ответа.
- `LAST` является последней зарегистрированной сделкой; `BID`/`OFFER` являются публичной справочной рыночной информацией и не гарантируют доступность через брокера.
- Для покупки, доступности лота и покупательной способности приоритет остаётся у broker gateway `getMarketSnapshot` по точному UID.
- MOEX snapshot допускается для независимой сверки, оценки расхождения и информационного отображения. Не усреднять его с broker snapshot.
- При `unavailable`, identity/schema/time/price mismatch показывать недоступность и безопасный error code; не переносить старое значение без отдельного cache/freshness контракта.
- Не хранить сырой JSON, upstream body, exception text, cookies или credentials.
- Публичная котировка MOEX не разрешает сделку, не является торговой рекомендацией и не меняет `trading_methods=false`.

## 14. Cache и freshness котировки MOEX ISS TQBR

- Использовать только `MoexIssTqbrQuoteCacheResultV1`; не читать process-local cache напрямую.
- Cache identity — точная пара `TQBR + normalized SECID`. Нельзя использовать snapshot другого тикера или board.
- `fresh_until` и `stale_until` определяются от `snapshot.retrieved_at` и управляют частотой refresh/retention.
- `age_seconds` определяется от `snapshot.quote.as_of` и отражает возраст рыночного наблюдения. Свежий HTTP-ответ не обнуляет возраст задержанной котировки.
- `fresh` разрешает информационный показ только с сохранением delayed/non-realtime/informational flags.
- Fresh cache hit должен иметь `served_from_cache=true`, `refresh_attempted=false`.
- Неудачный force refresh при ещё свежем cache допускает показ прежнего snapshot только как explicit `fresh` fallback с `refresh_attempted=true`, `refresh_succeeded=false` и безопасным cache error code.
- После fresh TTL snapshot считается stale. Показ разрешён только после неудачного refresh и explicit trusted `allow_stale=true`.
- Без `allow_stale=true` вернуть `unavailable` без snapshot, даже если stale entry физически ещё хранится.
- После stale expiry entry удаляется и не может быть показан.
- Wrong type, SECID/board/instrument mismatch, future timestamps и source unavailable fail closed.
- Cache очищается при restart; наличие прежней котировки не гарантируется.
- Не подменять unavailable значением из web search, другого ticker, broker snapshot или предыдущего процесса.
- Не усреднять MOEX cache value с broker `getMarketSnapshot`; источник, as_of, retrieved_at и freshness показывать раздельно.
- Cache не даёт торговых полномочий, не гарантирует real-time и не меняет `trading_methods=false`.
