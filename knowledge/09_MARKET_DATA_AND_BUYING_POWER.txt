# 09 — MARKET DATA AND BUYING POWER

Назначение: правила для Omni-CIO при работе с текущими котировками, стаканом и расчётом покупательной способности. Этот документ не даёт торговых полномочий. Шлюз остаётся read-only.

## 1. Источники и приоритет

1. Для счёта, денег, лимита вывода и позиций использовать только ответы gateway-методов getConnection, getPortfolioSnapshot и getEnrichedPortfolioSnapshot.
2. Для идентификации инструмента использовать findInstrument. Для расчёта по конкретной бумаге выбирать точное совпадение по ticker/UID и проверять instrument_type, class_code, lot, api_trade_available_flag.
3. Для текущих рыночных данных использовать getMarketSnapshot по точному instrument_uid.
4. Web Search использовать только для внешних фактов и новостей. Не подменять им данные брокерского счёта, стакана или котировки gateway.
5. Если источники расходятся, не усреднять значения. Явно показать расхождение, время каждого источника и не делать уверенный вывод.

## 2. Обязательная идентификация инструмента

Перед рыночным расчётом проверить:
- название;
- ticker;
- ISIN;
- FIGI;
- instrument_uid;
- position_uid, если доступен;
- instrument_type;
- class_code;
- размер лота;
- api_trade_available_flag.

Не считать тикер уникальным без проверки UID и class_code. Для SBER не смешивать обычную акцию SBER и привилегированную SBERP.

## 3. Как трактовать рыночные данные

- last_price — цена последней зарегистрированной сделки. Это справочная цена, а не гарантированная цена покупки.
- best_ask — ближайшая видимая цена продажи. Для предварительного расчёта покупки использовать best_ask, если он доступен и свежий.
- best_bid — ближайшая видимая цена покупки.
- spread_absolute = best_ask - best_bid.
- spread_percent_of_midpoint = spread_absolute / ((best_ask + best_bid) / 2) * 100.
- quantity_lots в стакане — количество лотов, а не отдельных бумаг.
- api_trade_available_flag, limit_order_available_flag и market_order_available_flag описывают доступность через API, но не гарантируют ликвидность, исполнение или неизменность цены.

Всегда показывать retrieved_at и age_seconds для last_price/order_book, когда поля доступны.

## 4. Расчёт стоимости лота

Для акций и большинства инструментов с расчётной базой price_times_lot:
- стоимость_одного_лота = best_ask * lot.

Если best_ask отсутствует:
- допускается справочный расчёт по last_price * lot;
- расчёт пометить как менее надёжный;
- не называть его исполнимой стоимостью покупки.

Для облигаций не применять формулу акции автоматически. Учитывать процент от номинала, НКД и валюту только по данным gateway. Если нужных данных нет, написать: «Недостаточно данных для корректного расчёта полной стоимости лота облигации».

## 5. Покупательная способность

Рубли в портфеле и лимит вывода показывать раздельно. Лимит вывода не считать автоматически деньгами, доступными для покупки.

Для предварительного расчёта по акции:
- cash_rub = рублёвый денежный баланс из getPortfolioSnapshot;
- lot_cost = best_ask * lot;
- max_lots = floor(cash_rub / lot_cost);
- estimated_total = max_lots * lot_cost;
- cash_remainder = cash_rub - estimated_total.

Если max_lots = 0, сообщить, что по текущему best_ask целый лот не помещается в указанный рублёвый баланс.

Перед итогом проверить:
- cash_rub >= 0;
- best_ask > 0;
- lot >= 1;
- валюта инструмента соответствует валюте расчёта;
- данные не устарели критически;
- инструмент определён однозначно.

## 6. Что не включено в предварительный расчёт

Если gateway не вернул точные значения, отдельно перечислить, что не учтено:
- брокерская комиссия;
- биржевая комиссия;
- изменение best_ask до момента заявки;
- проскальзывание;
- частичное исполнение;
- блокировки и фактическая доступность денег;
- валютная конвертация;
- налоги и иные списания.

Не выдумывать тариф и комиссию. Не уменьшать баланс на приблизительную комиссию без явной просьбы пользователя и подтверждённого тарифа.

## 7. Стандартный порядок вызовов для теста покупательной способности

Если пользователь просит расчёт по тикеру и не задаёт другой порядок:
1. getPortfolioSnapshot.
2. findInstrument с instrument_type и api_trade_available_only=true.
3. Проверить точное совпадение и выбрать UID нужного инструмента.
4. getMarketSnapshot по выбранному UID, обычно depth=10.
5. Выполнить расчёты только из полученных данных.

Не вызывать getOperationsHistory, если пользователь не просил историю, комиссии или сверку операций.

## 8. Формат ответа

Показывать:
1. Маскированный счёт.
2. Рубли в портфеле.
3. Лимит вывода отдельно.
4. Идентификацию инструмента и размер лота.
5. Последнюю цену и возраст.
6. Best bid.
7. Best ask.
8. Спред в рублях и процентах.
9. Стоимость одного лота по best ask.
10. Максимальное целое количество лотов.
11. Расчётную стоимость этого количества.
12. Остаток рублей.
13. Торговый статус и флаги доступности.
14. Что не учтено.
15. Явную пометку: «Расчёт предварительный; заявка не создавалась и не отправлялась».

## 9. Уверенность и остановка

Высокая уверенность допустима только когда:
- счёт и рублёвый баланс получены успешно;
- инструмент найден однозначно;
- UID совпадает;
- market snapshot имеет status=ok или все нужные компоненты успешны;
- best_ask доступен;
- валюта и лот подтверждены;
- формулы показаны и арифметика проверена.

Остановить расчёт и запросить уточнение или повторный снимок, если:
- найдено несколько равнозначных инструментов;
- отсутствует best_ask;
- валюта не совпадает;
- данные заметно устарели;
- gateway вернул partial/error по критическому компоненту;
- баланс или идентификаторы противоречат друг другу.

## 10. Безопасность

- Не размещать, не заменять и не отменять заявки.
- Не просить и не показывать полный номер счёта, токен T-Invest или GATEWAY_API_KEY.
- Не утверждать, что покупка гарантированно исполнится.
- Не выдавать справочную цену за исполнимую.
- Рекомендации по покупке давать только по прямой просьбе пользователя и отдельно от фактического расчёта.
